# 架构加深（第七轮）：回合的结果和「开口」在一处判定，文字回合和通话回合共用

Status: ready-for-agent

术语以 `GLOSSARY.md` 为准；本轮收窄了「开口」的定义（见下）。设计词汇（module、interface、seam、adapter、depth、leverage、locality）取自 `codebase-design` skill。这是 2026-10-07 架构审查里的候选 3，经 grilling 定下设计。只改 `backend/`，`GLOSSARY.md` 已在 grilling 时改好。

第五轮把放行与收尾收进了 `Admissions`（管「一次使用」），第六轮让租约自带身份和计量。这一轮管「一个回合的结果」。

## Problem Statement

- **「回合的结果」写在三处，三处不一样。** 文字回合由 `TurnOutcome` 判定：完成为成功，失败事件为失败或被拒绝，都没有就算离开。通话回合由 `CallTurns` 自己存一份结果，借用同一个事件判定函数，回合被截断时再问 `CallOutcome.turn_cut_short()`：通话因故障结束的算失败，否则算离开。运行记录写入时（`ActivityLog._write`）还有第三处：通话的记录写入时，还没收尾的回合一律补成离开，不看是不是故障截断的。第三处已经复现：通话取消时，取消在 `CallTurns` 或它上游卡住超过 pipeline 的取消超时（20 秒），通话会先于回合收尾，因语音服务故障被截断的回合被写成「离开」，之后回合自己的收尾因为「只算第一次」而不起作用。
- **「开口」有两个定义。** `TurnTaking` 的定义是「这条回复」开口：有文字送进 TTS 之后声音开始播放才算；上一条回复的声音还在播时，这条的第一句送进 TTS 就算。运行记录里的「到开口」耗时（`time_to_speak_ms`，看板的「到开口」）却是 `CallTurns` 看到任何一个 `BotStartedSpeakingFrame` 就记。两种偏差都已复现：
  - 上一回合或被放下的回复的声音迟到，被记成新回合的开口（测试里记成 109 ms，回复其实约 513 ms 才送进 TTS）。现实中多是打字发出时的毫秒级竞态。
  - 上一条回复的声音还在播时，输出端不会再发 `BotStartedSpeakingFrame`，这个回合的「到开口」一直为空。按现在的打断路径基本走不到，碰上时记录缺这一项。
- **词表里「开口」混进了「能不能打断」的规则。** 原定义含「回复已经记下的，也算已经开口」。那是补充和打断的条件，不是角色真的出声；照它计时，TTS 慢时「到开口」会早于她出声。
- **「被拒绝」靠比较提示文字。** 回合结果用 `event.message in (BLANK, TOO_LONG)` 区分被拒绝和失败；改一个字，被拒绝的回合就记成失败。
- **通话回合的结果不好测。** 现在要测一个通话回合的结果，得用 `CallUnderTest` 跑一次通话，再用 admin 客户端轮询看板。

## Solution

一个回合一份 `TurnOutcome`，文字回合和通话回合都把事件喂给它，由它一处判定结果、记下「开口」、收尾一次。「开口」只有一个意思，由 `TurnTaking`（通话）或回复的第一句（文字回合）报告。通话收尾时，由 `CallOutcome` 用同一套判定把还开着的回合收掉，写入运行记录的那一层不再决定结果。被拒绝是一种事件，不再比较字符串。

## User Stories

1. 作为管理者，我想看板上通话回合的「到开口」是角色这条回复真正出声的时间，不被上一条回复迟到的声音提前。
2. 作为管理者，我想上一条回复的声音还没停、这条回复已经接着说的回合，也有「到开口」的记录。
3. 作为管理者，我想只看文字的通话回合和文字回合，「到开口」都按回复的第一句出现计。
4. 作为管理者，我想一个回合里，被补充放下的那次回复如果已经开口，这个回合的「到开口」按那一次计，因为用户确实听到她开始说了。
5. 作为管理者，我想回复已经记下、声音却因 TTS 慢还没出来的回合，「到开口」按声音真正开始的时间计，而不是记下的时间。
6. 作为管理者，我想因语音服务故障结束的通话里，被截断的回合在运行记录里记为失败，即使通话的收尾早于回合的收尾。
7. 作为管理者，我想用户挂断、离开对话页、被封禁、到达上限等结束的通话里，被截断的回合记为离开，和现在一样。
8. 作为管理者，我想输入为空或太长的回合始终记为被拒绝，不因改了提示文字就记成失败。
9. 作为用户，我想限额的计法不变：成功和离开的回合计入，失败和被拒绝的不计入。
10. 作为用户，我想浏览器收到的事件不变：被拒绝的回合照旧收到 `type: "error"` 和同样的提示文字。
11. 作为用户，我想通话里补充和打断的规则不变：回复已经记下、有完整的一段时可以打断，和以前一样。
12. 作为开发者，我想回合结果的规则只写在一处，文字回合和通话回合共用。
13. 作为开发者，我想不跑通话、不经 HTTP，就能用纯单元测试覆盖回合结果的全部规则。
14. 作为开发者，我想「开口」只从 `TurnTaking` 来，`CallTurns` 不再看原始的出声帧去记时间。
15. 作为开发者，我想运行记录的写入只负责写，不决定任何结果。

## Implementation Decisions

### `TurnOutcome`：一个回合一份结果判定

- 每个回合一份，文字回合和通话回合共用。构造时给它这个回合的运行记录，和收尾时把结果交给谁（文字回合交给 `Admission.settle`，由它决定计不计入限额、写记录；通话回合交给回合记录的 `finish`）。
- interface：
  - `see(event)`：回合事件。完成为成功，`TurnRejected` 为被拒绝，`TurnFailed` 为失败；一个回合里有几条回复（补充后重新回复）时，以最后一个结果为准，和现在一样。其他事件不影响结果。
  - `began_speaking()`：角色开口了。只算第一次，记下从回合开始到这时的耗时（运行记录的 `spoke()`）。
  - `over(cut_short_by_failure: bool)`：回合结束了。有结果就用结果；没有的，`cut_short_by_failure` 为真记失败，否则记离开。只收尾第一次，之后再调不起作用。
- `see` 不再因 `SegmentDelta` 自己记开口；文字回合的调用方在回复的第一句出现时调 `began_speaking()`。
- 文字回合：`app.py` 照旧用它包住整个回合，结束时（正常结束、出错、页面离开，包括回合还没开始就离开）调 `over(False)`。
- 删掉独立的 `turn_result()` 函数。

### `TurnRejected`

- 引擎对空输入、太长的输入发 `TurnRejected`，别的失败照旧发 `TurnFailed`。它进入 `TurnEvent`，发给浏览器时和 `TurnFailed` 一样是 `type: "error"` 加 `message`，协议不变，前端不改。

### `TurnTaking` 发 `Spoke()`

- 新命令 `Spoke()`：每条回复在真正开口的那一刻发一次：
  - 要出声的回复：有文字送进 TTS 之后，角色的声音开始播放；或者送进第一句时，上一条回复的声音还在播；
  - 只看文字的回复（包括被打断后不再出声的）：第一句出现时。
- 回复记下仍让这条回复可以被打断，但不发 `Spoke()`；之后声音真正开始时照发。所以 `TurnTaking` 里「已开口、可以打断」和「已经报告过开口」分开记。
- `CallTurns` 执行 `Spoke()` 时调当前回合的 `TurnOutcome.began_speaking()`。删掉它在 `BotStartedSpeakingFrame` 和只看文字的 `SegmentDelta` 上直接记开口的两处。

### `CallOutcome` 管通话里开着的回合

- `turn_begun(own_llm)` 改为返回这个回合的 `TurnOutcome`，并记住它，直到它收尾。
- 新增一个只读的「通话是否因故障结束」（`ended_by` 为 failed）。`CallTurns` 的回合结束时（`_turn` 的 finally）调 `turn.over(这个值)`。
- `settle()` 先把还开着的回合按同样的值收掉，再收通话。设置失败（`set_up_failed`）时没有回合，不受影响。
- 删掉 `turn_cut_short()`；`CallTurns` 不再存 `_result`，`_recording` 换成当前回合的 `TurnOutcome`（emotion 等仍按通话记录记服务调用）。

### 运行记录

- `ActivityLog._write` 不再把没收尾的回合补成离开，只写入；写入时每个回合都应已有结果（已有的断言覆盖）。
- 运行记录的表结构、看板的统计不变。

### 词表（grilling 时已改）

- 「开口」：这条回复的声音开始播放；只看文字时指回复的第一句出现。
- 「补充」「打断」的条件改写为「角色已经开口（或者回复已经记下），回复也已经有完整的一段」，规则不变。

## Testing Decisions

- **好的测试**经由 module 的 interface 断言可以观察到的结果：回合的结果、计不计入限额、运行记录里的「到开口」、`TurnTaking` 交回的命令、浏览器收到的事件。不检查内部状态。先写会失败的测试（`/tdd`），再改实现。
- **`TurnOutcome`**：新的纯单元测试，表驱动（仿 `test_call_outcome.py`、`test_admission.py`）：各种事件序列加上「是否因故障截断」得出的结果；最后一个结果为准；只收尾一次；开口只记第一次，没开口的没有耗时。
- **`TurnTaking`**：在 `test_turn_taking.py` 补 `Spoke()` 的表驱动用例：送进 TTS 前响起的声音不算；送进 TTS 后声音开始算；上一条的声音还在播时送进第一句就算；只看文字时第一句算；回复记下不发、之后声音开始照发；每条回复只发一次，补充后的新回复再发一次。
- **`CallOutcome`**：在 `test_call_outcome.py` 补：收尾时开着的回合，通话因故障结束的记失败，否则记离开；回合已经收尾的不再改。
- **通话层回归**（`CallUnderTest`，仿 `test_call_records.py` / `test_call_turns.py`）：
  - 新回合开始后迟到的 `BotStartedSpeakingFrame` 不算这个回合的开口；
  - 上一条回复的声音还在播（只有 `BotStartedSpeakingFrame`、没有 `BotStoppedSpeakingFrame`）时，下一个回合仍记下「到开口」；
  - 取消在 `CallTurns` 上游卡住超过取消超时、通话先收尾时，因故障截断的回合记为失败。
- `test_call_records.py` 里经看板轮询断言回合结果的用例（「通话的回合按结果记在通话下」），能由上面单元层覆盖的断言挪下去；仍需要整条通话路径的（补充不另算回合、打断照常算回合）留在原处。
- 文字回合：`test_text_turn.py` 等现有测试照旧通过，补一条被拒绝的回合记为被拒绝、不计入限额（如果还没有）。
- `backend/` 下 `pytest` 全部通过，`ruff` 和 `pyright` 没有新的报错。
