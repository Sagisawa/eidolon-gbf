# 11: 拍板：每段语音开始播放的信号怎么做

Type: grilling
Status: resolved
Blocked by: none

## Question

「拍板：口型跟什么走」定了情绪在这段声音开始播放时切换，但「调研：pipecat 怎么知道每段语音什么时候开始播放」发现，Fish 的流式合成不给段落边界，要么每段单独开一次 Fish 会话（简单版，每段开头可能多一段停顿，要实测），要么各段会话并行（完整版，改动大，要确认 Fish 允许同时开两个会话），要么放宽要求（例如按 `bot-tts-text` 逐句的时机近似，早 1–4 秒）。选哪一种？要不要先做一次实测（简单版每段多出的停顿有多长）再决定？

## Answer

2026-09-30 与用户 grilling 定下，依据一次实测（脚本和原始数据在测量机的 `%TEMP%\fishbench\`，没有进仓库）。

**标准**：分段不能带来听得出来的额外停顿（约 0.2 秒以内算听不出来）。立绘是锦上添花，不能让通话变卡。

**实测**（设置和线上一致：`wss://api.fish.audio/v1/tts/live`、`s2.1-pro-free`、真乃的音色、24kHz PCM、`latency=balanced`，逐句发送加 flush，每种情况 9 次，每条回复 3 段、每段 4–8 秒音频）：

| 方案 | 前一段合成完 → 下一段首个音频（p50 / p95） | 段落边界的余量（下一段首个音频到达时，上一段还剩多少没播完） |
|---|---|---|
| 简单版（每段现开会话） | 2.48 / 3.86 秒，最长 5.3 秒 | 18 个边界里 9 个为负，最差 −3.82 秒：会多出听得出来的停顿 |
| 简单版 + 预先开好备用连接 | 0.92 / 1.61 秒 | 18 个边界全部为正，最小 +0.51 秒：不会多出停顿 |

- 问题出在建立连接（WebSocket 加开始消息要 0.6–3.6 秒），不在合成本身：文字送出后约 0.8 秒就有首个音频。
- 备用连接空等约 7 秒，Fish 也没有断开。
- 同一个 key 同时开 3 个会话都正常，没有报错也没有被限速，首个音频 0.73–0.79 秒。
- 限制：实测假设每段文字一下子就齐了；真实通话里文字是边生成边送来的，但这一点现在就存在，分段不会让它更慢。

**定下的方案**：
1. **每段一个 Fish 会话，并预先开好下一个连接**：当前段在合成时，就把下一段要用的连接打开等着；当前段结束（`stop` 后等到 `finish`）后，立即在备用连接上开始下一段。
2. **段落开始的标记**：在第 N 段第一块音频之前，往音频队列里插一条 `OutputTransportMessageFrame`（RTVI server-message，例如 `{type: "segment-playing", reply, segment}`），由输出传输层按播放节奏发出，前端据此切换这段的情绪和点头（机制见「调研：pipecat 怎么知道每段语音什么时候开始播放」）。
3. **在段落边界主动 flush**：顺手修掉「每段最后一句要等下一段的中文字幕生成后才送去合成」。
4. **后备**：如果上线后发现预先开连接不够稳，就改成各段会话并行合成、按顺序接起来（已确认 Fish 允许同时开多个会话）。
