# 世界设定、歌曲、唱片与演出：让角色知道作品世界的基本事实，而不是靠模型的记忆编

Status: ready-for-agent

术语以 `CONTEXT.md` 为准：「世界设定」「组合」「歌曲」「唱片」「演出」「声优」几个词条在 2026-09-28 的 grilling 中定下。为什么现实中的唱片和演出算作角色自己的经历、声优却只作系统内部数据，以及资料为什么以官方为准、导入后人工审核，见 `docs/adr/0008-real-world-releases-and-lives-are-in-character.md`。拆成六张 ticket（`issues/`）：01 没有前置；02、03、04 依赖 01；05 依赖 03 和 04；06 依赖 05。

## Problem Statement

制作人和角色聊天时，常常会聊到作品世界里的基本事实：事务所有哪些组合、谁和谁是一个组合的、她唱过哪些歌、那张 CD 什么时候发售、她站上过哪些舞台、下个月的 live 在哪里办。现在系统里只有剧情库、每位角色自己的人设和角色资料：

- 组合和成员只零散地写在各人的人设和角色资料里，没有所有角色共用的一份名单；还没写资料的角色对别的组合一无所知。
- 歌曲、唱片、演出完全没有收录。

系统不接搜索，所以问到这些事时，角色只能凭对话模型训练时的记忆回答。这种回答常常是错的：把歌安到别的组合头上，编一个不存在的发售日，声称自己上了没上过的舞台。熟悉作品的制作人一眼就能看出来，角色「像不像本人」也就垮了。

## Solution

给系统加上一份由我们整理、可以查证的作品事实，分两层交给角色：

- **每个回合都带上的**：
  - 世界设定：283 事务所的社长和事务员、八个组合各有哪些偶像。
  - 这位角色自己的歌：她的个人曲和她所在组合的歌。
  - 她上过的演出（包括已经公布、还没举办的）。
  - 资料截止日，以及查不到时怎么办的规则。
- **按需检索的**：全作品的歌曲、唱片、演出和逐日曲目单。和剧情、角色资料一起检索，一起排序。

资料由一个导入命令从官方网站和几个粉丝整理站抓取、合并，生成一份结构化资料文件提交进仓库。每次导入后由人看过 diff 再提交；资料截止日就是这次导入的日期。

在角色看来，现实中发售的唱片就是她们自己发行的唱片，现实中的演出就是她们站上的舞台。她知道名称、日期、会场、出演者、曲目单，但不知道台上具体发生了什么，也不编。她的声优实际出演的场次才算她上过；声优只用来做这个判断，角色不知道，任何提示里都不出现。资料里查不到的，角色老实说想不起来，既不否认也不附和。

## User Stories

1. 作为制作人，我问真乃「イルミネのメンバーって誰だっけ」，她能准确说出三个人，不会多也不会少。
2. 作为制作人，我问恋鐘「ストレイライトって誰がいるの」，即使她自己的资料里没写，她也能答对。
3. 作为制作人，我提到新加入事务所的偶像（例如 CoMETIK 的成员），任何一位角色都认识她、知道她在哪个组合，即使这位角色早期的剧情里还没有她。
4. 作为制作人，我问角色「社長さんの名前は？」「はづきさんって何してる人？」，她能答对。
5. 作为制作人，我问角色她唱过哪些个人曲，她能说出资料里的曲名，不编不存在的歌。
6. 作为制作人，我问「イルミネの曲で一番好きなのは？」，她从真实存在的组合曲里挑一首来聊。
7. 作为制作人，我问某首歌收在哪张 CD 里、什么时候发售的，她能按资料回答。
8. 作为制作人，我问一首别的组合的歌是谁唱的，她能通过检索答对。
9. 作为制作人，我问一首特别组合唱的歌（例如 Team.Luna 这类），她知道这是哪几位偶像一起唱的，但不会把特别组合当成谁的所属组合。
10. 作为制作人，我问她是哪个组合的，她只会说她的常设组合。
11. 作为制作人，我提到一首她不认识的歌（资料里没有，或者我记错了名字），她老实说想不起来，不会说「没有这首歌」，也不会顺着我编下去。
12. 作为制作人，我让她唱几句某首歌的歌词，她不会引用或编造歌词，而是用角色的方式岔开（比如说想在舞台上唱给我听）。
13. 作为制作人，我问她站上过哪些舞台，她能按资料列出她上过的演出，以及大致的日期和会场。
14. 作为制作人，我问「6th ライブの Day1 でどんな曲を歌った？」，她能按曲目单回答，只说她那天唱过的歌。
15. 作为制作人，我问一场她的声优缺席的演出，她知道有这场演出，但不说自己上了台，也不编缺席的理由。
16. 作为制作人，我问一场只有其他组合出演的演出，她知道这场演出，但不说自己上了台。
17. 作为制作人，我问和其他品牌合办的演出（例如 MOIW），她知道自己上过，但不去描述其他品牌的偶像是谁。
18. 作为制作人，我问合办演出上翻唱的其他品牌的歌，她知道那天唱过这首，但不把它当成自己的歌。
19. 作为制作人，我问「那天台上发生了什么」「MC 说了什么」，她不编现场的情节，只说得出资料里的事实和她的感受。
20. 作为制作人，我问下个月的 live，她能根据当前日期说出「来月の○○、楽しみですね」，日期、会场和资料一致。
21. 作为制作人，我问一场已经公布、还没发售的 CD，她知道发售日，说起来是「期待」而不是「已经发了」。
22. 作为制作人，资料截止日以后才公布的演出或 CD，她不会编，而是说还没听说。
23. 作为制作人，我问她的声优是谁、「中の人」是谁，她用戏里的方式应对，不说出任何声优的名字。
24. 作为制作人，我问她某个周边商品（立牌、徽章），她不编具体商品，用戏里的方式应对。
25. 作为制作人，我问「那次 live 是怎么样的」这类回顾经过的问题，她不会因为剧情库里没有这段经过，就说自己「没有经历过」。
26. 作为部署者，我运行一条命令就能从各个来源导入最新的资料，生成资料文件和一份导入报告。
27. 作为部署者，我能在导入报告里看到来源之间对不上的地方（比如官方和粉丝整理的曲目单不同）、只在粉丝来源里有而没有官方新闻链接的缺席、以及没能对应到某位偶像的演唱者或出演者，由我决定怎么处理。
28. 作为部署者，我能用 git diff 看出这次导入改了哪些资料，确认无误后再提交。
29. 作为部署者，资料文件提交进仓库以后，换一台机器部署不需要重新导入。
30. 作为部署者，某个来源暂时访问不了时，导入命令明确报错，不会生成一份缺了一块的资料文件把旧的覆盖掉。
31. 作为部署者，我新加一位角色时，只要她的名字和资料里的偶像对得上，世界设定、她的歌和她的演出就自动带上，不需要另外写。
32. 作为部署者，角色配置里某位角色的名字在资料里找不到时，启动直接报错说明是哪位角色，而不是悄悄不带她的歌和演出。
33. 作为部署者，还没导入过资料时，系统照常运行，只是没有这一层，日志里说明原因。
34. 作为部署者，资料文件改了以后，重启后端就生效，检索用的向量只为改动的条目重新计算，不需要另外跑命令。
35. 作为部署者，更换 embedding 模型后，资料的向量和角色资料的一样按新模型重算。
36. 作为写人设的人，人设里只写她和组合伙伴的关系，不再列成员名单；生成人设初稿的命令也按这个结构出稿。
37. 作为维护者，我能从资料文件里看出每一条是从哪个来源来的，方便核对。

## Implementation Decisions

### 资料文件

- 一份结构化资料文件（JSON），提交进仓库，放在和角色配置同级的资料目录里。数据是公开的事实，不属于 ADR-0003 限制的剧情库数据。
- 内容：
  - **资料截止日**：导入的日期。
  - **事务所**：社长、事务员。
  - **偶像名单**：每位偶像的日文全名、读音、所属组合、声优。声优只在导入时用来对应演出出演者，也留给人核对，不进入任何提示。
  - **组合**：八个常设组合，各有名称、读音和成员。特别组合不列在这里。
  - **歌曲**：曲名、演唱者（偶像列表；是特别组合唱的，另记特别组合名）、收录它的唱片。
  - **唱片**：名称、发售日、品番、曲目（按顺序，引用歌曲）。
  - **演出**：名称、会场，以及每个演出日的日期、闪耀色彩这边的出演偶像和曲目单。曲目单的每一项是曲名和演唱的偶像，伴舞不算演唱。翻唱的其他品牌歌曲照实记下，但不因此成为「歌曲」。其他品牌的出演者不记录。
  - 每一条都带来源（URL）。
- 已经公布但还没发售、还没举办的唱片和演出同样收录，从日期就能看出。
- 实体周边、歌词、作词作曲编曲不收。

### 导入命令

- 新增一条后台命令（和 `story sync` 同级，例如 `world sync`），手动运行，不做定时任务。
- 各类数据的来源（2026-09-28 实测可用）：
  - **偶像、组合、声优、社长和事务员**：im@sparql 的 SPARQL 接口，查询时品牌要写 `"ShinyColors"@en`；组合用官方站点的组合页（`shinycolors.idolmaster-official.jp/idol/<unit>`）核对。常设组合以官方组合页为准，im@sparql 里多出来的特别组合不算。
  - **唱片、曲目、演唱者**：Lantis 的闪耀色彩站点，发售列表和各张唱片的页面。曲目行的格式是「曲名 / 角色 (CV.声优)」，从中解析出演唱者。imas-db 补齐 Lantis 缺少的部分。
  - **演出列表**：偶像大师官方门户的 CMS API。先取 token，再按 `LIVE-EVENT` 分类列出所有公演，在本地按品牌 `SHINYCOLORS` 筛选；在请求里按品牌过滤会返回 0 条。
  - **逐日出演者和缺席**：wikiwiki 的「ライブイベント情報」。缺席写在脚注里，要把脚注和出演者对应起来。
  - **曲目单**：imas-db 的公演页，已经按演出日分开列出。
- 合并规则：
  - 官方来源有的字段以官方为准。
  - 粉丝来源的缺席只有附了官方新闻链接的才采用；没附链接的不采用，列进导入报告。
  - 来源之间有冲突时，按官方优先的结果写入，冲突列进导入报告。
  - 演唱者和出演者按「角色名」或「声优 → 偶像」对应到偶像名单；对应不上的列进导入报告，这一项不写入。
- 任何一个来源抓取失败，命令就报错退出，不写资料文件。只有全部成功时才整体替换旧文件。
- 导入报告打印到终端：各类条目的数量、相对于旧文件的增减，以及上面几类需要人工处理的事项。

### 世界设定和角色的对应

- 角色配置里每位角色，按显示名（日文全名，例如「櫻木真乃」）对应到资料里的偶像。
- 资料文件存在、却有角色对应不上时，启动失败，报错里写明是哪位角色，和现有的角色配置错误一样处理。
- 资料文件不存在时，系统照常运行，不带这一层，日志说明原因。

### 每个回合都带上的部分

- 系统提示在人设之后，多一节由资料生成的「世界设定」。以下内容每个回合都带上：
  - 资料截止日。
  - 283 事务所的社长和事务员。
  - 八个组合各有哪些偶像。
  - **她的歌**：演唱者正好是她一个人的歌，和演唱者正好是她所在组合全体成员的歌；每首附上收录的唱片名和发售日。
  - **她上过的演出**：她出演的每个演出日的演出名、日期、会场，包括还没举办的。
  - **规则**：
    - 资料里查不到的歌曲、唱片、演出，老实说想不起来，既不否认也不附和。
    - 不引用、不编造歌词。
    - 只知道演出的事实，不编造台上发生了什么。
    - 不谈论声优。
    - 不谈论具体的周边商品。
    - 资料截止日以后的事一概不知道。
- 这一节不带任何声优名字。
- 「查不到就想不起来」这条规则放在所有角色共用的这一节里，而不是写进每个人的人设，这样新角色自动就有。

### 按需检索的部分

- 新增一个所有角色共享的资料索引，每个条目一段文字：
  - 每首歌曲一条：曲名、演唱者、收录唱片。
  - 每张唱片一条：名称、发售日、曲目。
  - 每个演出日一条：演出名、日期、会场、出演偶像、曲目单。
- 索引的行为照搬角色资料的索引：
  - 条目的向量在第一次检索时计算，存进 SQLite。
  - 按「文字 + 模型」为键，所以资料改了以后重启就生效，只重算改动的条目。
  - 旧模型的向量在切换模型时一并清掉。
- 检索参考资料时，资料索引的候选和剧情、角色资料的候选一起交给 reranker 统一排序，共用同一个相关度阈值和条数上限。
- 在提示里，这类参考资料用单独的标题（例如「资料」），说明是关于歌曲、唱片和演出的事实。
- Jev 判断是否需要检索时的说明文字，加上第三类资料：歌曲、唱片和演出。
- Jev 判断为「回顾经过」时，除了回忆剧情，也在资料索引里查一次。查到的演出或唱片条目和剧情一起带上。回忆剧情落空时的提示语也要改，不能再说「你没有经历过这件事」：剧情库里没有这段经过，不代表她没站上过那个舞台。
- 对话模型主动调用的 `recall_story` 工具仍然只查剧情。

### 人设

- 人设不再列组合成员名单，只写她和组合伙伴的关系：称呼、相处方式。
- 现有的几份人设按这个结构改写：真乃、恋鐘，还有 example。
- 生成人设初稿的命令把「组合成员」一节改成「与组合伙伴的关系」，出稿说明也相应改掉。

## Testing Decisions

- 好的测试只检查外部行为：导入命令生成的资料文件和导入报告，以及对话模型实际收到的提示。不测解析函数、合并函数、索引类本身。
- **导入接缝**：
  - 用假的 HTTP 站点，一次性模拟 im@sparql、官方组合页、Lantis、官方 CMS API、wikiwiki 和 imas-db 的响应，跑完整条导入命令。先例是剧情同步测试里的假镜像站点。
  - 要覆盖的情形：
    - 偶像、组合、社长和事务员齐全；特别组合不进组合列表。
    - Lantis 的曲目行被解析成正确的演唱者，特别组合唱的歌能拆到具体偶像。
    - 还没发售的唱片、还没举办的演出照样收录。
    - 在门户 API 的结果里，按品牌筛选出闪耀色彩的演出。
    - 附了官方新闻链接的缺席生效，该演出日的出演者里没有她；没附链接的缺席不生效，并列进报告。
    - 官方和粉丝来源冲突时以官方为准，并列进报告。
    - 对应不上的演唱者和出演者列进报告，不写入。
    - 其他品牌的出演者不写入；翻唱的其他品牌歌曲在曲目单里，但不在歌曲列表里。
    - 任何一个来源失败时命令报错，旧资料文件原样保留。
    - 每一条都带来源。
- **对话接缝**：
  - 从 `ConversationEngine.turn` 进入，用假的对话模型、Jev、embedder 和 reranker，检查对话模型收到的提示。先例是 `test_turns`、`test_retrieval`、`test_recall_story`。
  - 要覆盖的情形：
    - 世界设定、她的歌、她上过的演出、资料截止日和规则每个回合都在，而且只列她的歌和她的演出，不列别人的。
    - 声优的名字在任何提示里都不出现，包括常驻部分、检索到的资料和回顾经过的结果。
    - 声优缺席的演出日不算她上过的演出。
    - 检索参考资料时，歌曲、唱片、演出日条目能和剧情、角色资料一起被召回，放在「资料」标题下。
    - 回顾经过时也会带上资料索引的命中；剧情落空时，提示不再说「没有经历过」。
    - 没有资料文件时，回合照常进行，不带这一层。
  - 角色配置和资料对不上时启动失败：先例是 `test_characters`。
  - 人设初稿的新结构：先例是 `test_sheet_draft`。

## Out of Scope

- 实体周边、歌词、作词作曲编曲。
- 让角色谈论声优；在界面上展示声优。
- 定时或自动导入；对话中实时搜索。
- シャニソン 和动画的**剧情**进剧情库。歌曲和唱片不论出处都收，剧情不收。
- 其他品牌偶像的资料。合办演出里只记录闪耀色彩这边的出演者。
- 按剧情时间线决定角色认识谁。世界设定一律反映资料截止日时的现状。
- 为资料条目单独校准 rerank 阈值。先沿用参考资料的阈值，效果不好再用 `eval rerank` 调。

## Further Notes

- 常驻部分的长度要留意。按一个组合估算，她的歌有几十首，她上过的演出有十几二十个演出日，应该在可以接受的范围内。如果某位角色的列表明显偏长，优先压缩格式（比如同一场演出的几天合并成一行），不要改成按需检索：这部分正是最怕检索落空的。
- 资料文件和剧情库不同，是可以公开的事实，但里面有声优姓名。仓库是私有的，没有问题；仓库改为公开时，这一点和 ADR-0003 的其他条目一起重新考虑。
- 已经公布的演出延期、取消或追加场次后，要重新导入才会更正。导入报告里的增减，就是用来发现这类变化的。
