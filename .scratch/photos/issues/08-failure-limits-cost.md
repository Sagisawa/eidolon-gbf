# 08: 拍板：失败、限额和计费

Type: grilling
Status: resolved
Blocked by: 01, 04, 10

## Question

- 生图失败（超时、中转报错、被内容检查拦下）时：这个回合算失败（不留记录、不计入限额），还是她的话照常记下、只是照片没发出来（她说「拍坏了」）？自带 key 失败时按现有规则不悄悄改用部署者的，那照片怎么办。
- 限额：照片要不要单独的每小时上限（和回合数分开），默认多少，管理者能不能单独给某位用户设；计不计入、怎么在界面上体现。
- 免限额密钥：生图能不能被选进免限额密钥；文字回合现在「用了自带 LLM 就不计入」，带了自带 LLM 但没带生图 key 的回合发照片，算不算计入。
- 并发：一个 NovelAI 账号一次只能跑一张（以「NovelAI 官方图像 API 现状」查到的为准）时，部署者那一侧多人同时要照片怎么排队、排队多久算超时。
- 花费：生图按什么单位记（张？Anlas？），单价怎么填，看板上怎么显示；运行记录的服务名。
- 部署者没配生图时：她怎么回应要照片的请求（说手机没电？直接不提供这个能力？）。

## Comments

- 实测（「准备测试用的中转地址和 key」）：用户的中转 key 错误在 1 秒内回 401/403；A 形态模型名错误回 400；B 形态模型名错误 60 秒还没返回，所以超时一定要有。同时发 3 张都成功、没有 429，中转一侧不是严格的一次一张。单张 5–9 秒，并发时 13–16 秒。
- 「拍板：怎么触发、谁来写提示词」已定：部署者没配生图、用户也没自带时，不问判断模型、提示词里也不提照片，她不知道自己能发，表现和现在一样。所以「没配时她怎么回应」不用再定。到了照片的次数上限时，她用自己的话推掉，服务器要在回合开始前就知道这个回合还能不能发，好决定告诉她什么。生成是在她回复最前面的 `<photo>` 标签写完时开始的，和她说话的时间重叠。
- 「原型：外貌一致性」已定：用 V5 Curated，不用角色参考图。按「NovelAI 官方图像 API 现状」，Opus 免费只要 ≤1024×1024 像素、≤28 步、不带参考图、一次一张，所以单张费用不会因为参考图多出 5 Anlas。但 V5 会扣 Opus 用量条。用户中转的计费方式还不知道。
- 「拍板：全年龄怎么守」已定：生成后不查图，所以失败里没有「被内容检查拦下」这一种。黑名单命中时只剥掉那个 tag，照片照发，也不算失败。剩下要定的失败只有超时、中转或官方报错，还有中转回 200 却是错误图。
- 「拍板：照片存哪、留多久、谁能看」已定：照片存在 SQLite 的照片表里，算她那条回复的附件，生成完再挂上去；回复还在就存，页面关了也不取消生成。失败时记录里怎么显示（照片表里留一行失败的记录，还是什么都不留）在这张票定。每人存多少张不另设上限，靠这里的生成次数上限兜住。
- 「拍板：条款之下谁出钱」已定：部署者那一侧照旧，官方 token 和中转都能填，所以这张票的问题都不变。部署者填的若是官方 token，就是严格的一次一张，排队照样要定；用户自带的官方 token 同样一次一张，按各自的 token 分开排。

## Answer

2026-10-17 拷问定下（grilling + domain-modeling）。术语表不加词条，也不记 ADR：这些决定都好改，而且都沿用现有的限额、自带密钥和计价做法。现有代码的出处：限额在 `usage.py`、`admission.py`，免限额在 `own_keys.py:373-380`，计价在 `prices.py`、`activity.py`。

**失败：她的话照常记下，只是照片没发出来。**

- 照片生成时，她的回复已经流式发出去了，所以照片失败时，这个回合不算失败，记录照常保存。
- 照片表留一行失败记录，不带图片，记下原因：
  - 超时（包括排队超时）
  - 服务报错
  - 返回的图不对
  - 自带 key 失败
  - 次数用完（见下面的「什么时候查、什么时候扣」）

  前端在原来放照片的位置显示失败的占位，刷新后也还在，不同原因显示不同的提示。占位的样子和文案交给「原型：照片怎么呈现」。
- 之后的回合里，带回去的 `<photo>` 标签加上失败标记（例如 `status="failed"`），系统说明里加一句「标了失败的照片对方没收到」。用户问「照片呢」时，她能自然地接上。
- 不自动重试，也不给重试按钮。想要的话，用户再说一次，就是一个新的要照片的回合。重试按钮等于开一条不经过她就能生图的路。
- 从标签写完算起，总时限 90 秒，包括排队和生成，写死、不做配置。超时以后晚到的结果直接丢掉。
- 认错误图只看两点：响应能解开、里面有一张图；宽高和要求的一致。不一致都算失败。纯色检测不做。会把尺寸静默换掉的中转（像中转 B）因此用不了，`docs/configuration.md` 里写明需要什么样的中转。
- 自带生图 key 失败时，照现有规则不悄悄改用部署者的 key，错误里的 key 打码，提示指向设置页（和自带 LLM 失败一样）。

**限额：照片单独计次，每人每小时。**

- `usage` 表新加一种 `photo`，和回合、通话一样按人、按滑动一小时计数。
  - 全站默认每小时 5 张，`.env` 和后台「限额与玩法」页都能改，0 表示不限（和现有两项一样）。
  - `user_limits` 加一列 `photos_per_hour`，管理者给单个用户设限额的弹窗加上这一项，含义和现有两列一样：空值跟全站，-1 不限，0 只能用自带。
  - 环境变量的名字照现有的写法（`EIDOLON_PHOTOS_PER_HOUR`），最后由票 09 统一定。
- 什么时候查、什么时候扣：
  1. 回合开始时只查不扣。还有余量，照片说明照常写；用完了，说明改成「他在要照片，但你这会儿发不了」，她用自己的话推掉，写了标签也丢掉。
  2. 用完次数时，服务器同时把 `retry_at` 推给前端，界面上另外告诉用户「这一小时的照片已经用完，HH:MM 之后可以再要」，免得用户以为她在耍性子。怎么显示交给「原型：照片怎么呈现」。
  3. 标签写出来、要开始生成时才扣一张。如果这时恰好被别处用完（同一个人文字和通话同时在用），就按「次数用完」记成失败，不生成。
  4. 失败的照片把次数还回去，但花费照样记一条调用。
- 通话里的照片和文字回合的照片共用同一个次数。
- 不显示剩余几张：现在的回合和通话也不显示，照片照旧。

**免限额：只看这张照片花的是谁的钱。**

- 用自带生图 key 生成的照片不计入次数，`usage` 照样写一行 `exempt=1`；用部署者 key 生成的照片计入。
- 带了自带 LLM 但没带生图 key：回合本身照旧不计入，照片照样计入。
- 「生图」**不能**选进免限额密钥。免限额密钥只管回合和通话的次数，否则勾上生图以后，打电话也得带生图 key 才能免限额。
- 限额为 0（只能用自带）的用户没带生图 key 时，就当这个回合不能生图：不问判断模型，她也不知道自己能发照片（和「部署者没配生图」一样）。

**排队：按 token 排。**

- 对外的生图请求按 token 排队，每个 token 有一个「同时生成几张」的上限，等不到的先进先出。等待时间算进 90 秒的总时限，超时就按「超时」记成失败，请求根本没发出去。不另外限制队列长度。
- 部署者那一侧：配置里加一项「同时生成几张」，默认 1（官方 token 严格一次一张），用中转的管理者可以自己调高。放在后台哪一栏归票 09。
- 自带那一侧：每个用户自己的 key 固定一次一张，各排各的。

**花费：按张记。**

- 运行记录的服务名新加 `image`，中文叫「生图」（`activity.py` 的 `ServiceName`、前端 `dashboard.ts`、`zh.ts`）。
- 计量单位新加「张」（`images`），单价按每张填，不按每百万。`prices.py` 的 `PER`、后台设单价的接口（`admin_prices_api.py` 单位的 `Literal`）和前端的单位文案都要加。
- 预设单价：官方 `nai-diffusion-5-curated` 按付费 Anlas 的价格，每张 0.036 美元（832×1216、23 步、26 Anlas），标上查价日期。用 Opus 订阅时实际上在额度内不花钱，这个预设偏保守，接受。中转没有预设，由管理者自己填，没填就和现有没设单价的服务一样显示。自带 key 的调用照现有规则只统计用量、不计价。
- 每次生成都记一条调用，失败的带上错误原因。只有确实拿到了图（包括尺寸不对的错误图，中转多半已经扣了钱）才记 1 张用量；HTTP 报错、超时都记 0 张；排队超时的请求没发出去，不记调用。
- 这条调用挂在那个回合的运行记录下面（同一个 `record_id`），回合已经结束也一样。
