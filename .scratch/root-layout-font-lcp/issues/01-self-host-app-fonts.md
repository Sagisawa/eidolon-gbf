# 01: 应用根 layout 的 CJK 字体拖慢所有页面的 LCP

**Status:** ready-for-agent

**Blocked by:** None

## 现象

应用的根 layout（`frontend/src/app/(app)/layout.tsx`，落地页拆出去以后它就在 `(app)` 路由组里）用 `next/font/google` 加载 Noto Sans SC 和 LINE Seed JP。Google Fonts 按 unicode-range 把 CJK 字体切成很多片，next/font 为这些切片生成的 `@font-face` CSS 会阻塞渲染。

在落地页原型（`prototype/landing-page` 分支的 `3d07693`）的测量中顺带发现：`/privacy` 在手机 4G 节流下 LCP 约 3 秒，拦掉这些 CSS 后约 0.6 秒。所有挂在根 layout 下的页面都受影响。复测脚本在原型分支的 `frontend/scripts/landing-prototype-measure.mjs`。

## 范围

不并进落地页的规格：落地页会拆出自己的根 layout、自托管字体子集（ADR-0016 的 2026-10-10 修订），不受这个问题影响。这里只管应用本身的页面。

## 决定（2026-10-10 分诊）

- **预算**：应用页沿用落地页的口径，手机 4G 下 LCP ≤ 2.5 秒（Lighthouse 移动端默认节流，3 轮取中位数）。`/login`、`/privacy` 是硬门槛；登录后的 `/conversations` 和一个对话页只报数字，不卡验收（还掺着接口耗时）。
- **分步**：这张票只做第一步，零视觉变化的瘦身：Noto Sans SC 换成可变字体（一套切片代替四个字重各一套），LINE Seed JP 去掉没用上的 700。第一步不达标就停在检查点，第二步（自托管切片、字体 CSS 不阻塞渲染）拿实测数据再定。
- **排除**：中文正文退回系统字体（要改 DESIGN.md 的字体规范，Windows 上会从 Noto Sans SC 变成 Microsoft YaHei）；只预载常用切片（解决不了 CSS 阻塞）。
- **检查脚本**：main 上留一个应用页的人工检查脚本，以后改字体能再跑。
- **视觉验收**：去 700 要像素零差异；可变字体允许中文文字边缘的光栅化差异，报告差异像素数并拼前后对照图，由维护者过目放行。

## Comments

> *This was generated by AI during triage.*

### 分诊核实（2026-10-10）

对着当天的构建（`frontend/.next`）静态核实，现象成立：`/privacy` 的 HTML 里有三个阻塞渲染的样式表，一个是应用样式（170 KB，gzip 25 KB），另外两个全是 `@font-face`：Noto Sans SC 405 条（372 KB，gzip 134 KB），LINE Seed JP 248 条（188 KB，gzip 67 KB）。1.6 Mbps 下光这约 200 KB 就要 1 秒多。

查到的事实：

- next/font 的字体数据里 Noto Sans SC 有 `variable`（wght 100–900）；LINE Seed JP 没有，只有 100/400/700/800 几个静态字重。
- 应用里 `<Ja>` 用在对话气泡、通话层的字幕、换装选择器的卡名。外层字重只有 400 和 `font-medium`（500，浏览器在 400/700 里取 400），没看到要 700 的地方。
- main 上的 `frontend/scripts/landing-check.mjs` 已经有同一套 4G 节流的 LCP 测量；`frontend/scripts/screenshots.mts` 能拍登录、条款、隐私和登录后的各页（电脑/手机 × 浅色/深色），通话层不在里面。

## Agent Brief

**Category:** enhancement
**Summary:** 给应用的根 layout 的字体瘦身（Noto Sans SC 换可变字体，LINE Seed JP 只留 400），让不用登录的应用页在手机 4G 下 LCP ≤ 2.5 秒，视觉不变

**Current behavior:**
应用的根 layout（不是落地页那个）用 `next/font/google` 载入两套字体，都是 `preload: false`、只要 latin 子集，CJK 部分靠 Google 的 unicode-range 切片：
- `Noto_Sans_SC`，`weight: ["400", "500", "600", "700"]`，CSS 变量 `--font-zh`（正文字体栈 `--font-sans` 的第一位）
- `LINE_Seed_JP`，`weight: ["400", "700"]`，CSS 变量 `--font-ja`（`font-japanese` 的第一位，`<Ja>` 组件用它）

next/font 为每个字重的每个切片各生成一条 `@font-face`，打进几个阻塞渲染的样式表，gzip 后约 200 KB，比应用自己的样式（约 25 KB）大得多。挂在这个 layout 下的每一页首屏都要等它们下完。原型测得 `/privacy` 在手机 4G 下 LCP 约 3 秒。

**Desired behavior:**
1. **Noto Sans SC 换成可变字体**：next/font 不传具体字重（或者用 `"variable"`），用 wght 轴，一套切片覆盖所有字重。界面用到的 400/500/600/700 照常可用，`--font-zh` 这个变量名和正文字体栈不变。
2. **LINE Seed JP 只载 400**：先在代码里核实没有日语文字要 700（`<Ja>` 及所有用 `font-japanese` 的地方，包括继承来的字重）。真有地方用到就保留 700，在票里说明是哪儿。DESIGN.md 的 Typography 里「LINE Seed JP（…400/700…）」改成实际载入的字重。
3. **应用页检查脚本**：新增一个人工运行、不进 vitest 的脚本，写法照 `landing-check.mjs`（开头注释写清怎么起服务、怎么跑，构建版 `next build` + `next start`，不用 dev）。它测：
   - `/login`、`/privacy` 在手机 4G 节流下的 LCP（节流参数、视口、轮数、取中位数都和落地页检查脚本相同），每页 ≤ 2500 ms 才算通过，退出码反映通过与否；
   - 有开发登录（后端 `EIDOLON_DEV_LOGIN=1`）时，再测 `/conversations` 和一个对话页的 LCP，只打印数字，不影响退出码；没有就跳过并说明；
   - 每页的阻塞样式表个数和字体 CSS 的压缩后字节数，打印出来方便对比。
   LCP 测量能抽成两个脚本共用的小模块就抽；抽不干净就复制，落地页检查脚本的行为不能变。
4. **检查点**：两步改完后跑检查脚本。`/login` 或 `/privacy` 超预算就停下，不要自己做自托管或改加载方式：把改动前后的数字写进本票 `## Comments`，`Status` 改回 `needs-triage`。

**Key interfaces:**
- 应用根 layout 里 `Noto_Sans_SC(...)`、`LINE_Seed_JP(...)` 两个 next/font 调用的选项（`weight`、`subsets`、`variable`、`preload`）；`variable` 名 `--font-zh`、`--font-ja` 不改
- `globals.css` 里的 `--font-sans`、`--font-japanese` 字体栈：不该需要改，改了要说明理由
- `<Ja>` 组件：行为不变
- DESIGN.md 的 Typography 一节：只改字重的描述，其他规范不动
