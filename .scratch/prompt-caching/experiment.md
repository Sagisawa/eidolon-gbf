# 实验结果：几种排法、几种禁止调用的方式各命中多少缓存

票 03。2026-10-14 17:04 到 19:32 UTC（北京时间 10-15 01:04–03:32）跑完。脚本 `experiment.py`，每次请求的原始记录在 `experiment-data/<服务>.jsonl`，文末的明细表由 `experiment.py <服务> report` 生成。

## 怎么测的

- **服务**：
  - `deepseek-flash`（`https://api.deepseek.com/v1`，部署者的 key），线上用的。
  - 用户自己的第三方服务（`https://magpie-api.hmhnk.top/v1`）上的四个模型，用来检验结论是不是只在 DeepSeek 上成立：
    - `antigravity/gemini-3.8-flash`（记录名 `third`）；
    - `clinepass/cline-free/mimo-v2.6-flash`（`mimo`）；
    - `qwen-cn/qwen3.8-flash`（`qwen`）；
    - `qoder-cn/qfmodel`（`qoder`）。

    后三个是 Gemini 那组命中时有时无以后，用户提议加测的。
  - 都走 Chat Completions，流式，带 `include_usage`。都没设 `reasoning_effort`，和本地 `.env` 一样。线上后台要是设了思考强度，DeepSeek 的提示词开头会多一行强度说明，但每回合都一样，不影响下面的比较。`deepseek-flash` 不设强度时也在思考，每回合都有思考 token。
- **提示词**：
  - 用真的八宫巡人设、当天的世界设定、`FORMAT_INSTRUCTIONS` 和 `RECALL_STORY_TOOL`。消息由产品里的 `openai_compat._messages` 拼：开头连续的系统消息拼成一条，中途的原地发 `role: system`。
  - 制作人那段带当前时间（模拟时钟，每回合加 2 分钟），还有好感度那几行（亲近档，加一句每回合换的感受）。
  - 记忆是假的，每回合 3 条。参考资料是剧情库里真的剧情和角色资料，约六成回合带，每回合随机。预先回忆的剧情也取自剧情库，按 `recall_prompt` 排。
  - 同一个回合号在每种情况里拿到的动态内容都一样。
- **对话**：
  - 固定 10 句闲聊。模型的真实回复按 `format_reply` 重排后接进历史，和引擎一样。
  - 每种情况开头加一句「（会话编号 随机串）」，所以不会吃到别的情况或线上用户留下的缓存。也因此每种情况的第 1 回合都全部未命中，表里另给「去掉第 1 回合」的命中率。
  - 两次请求之间隔 6 秒。Gemini 另用 20 秒间隔重跑了一遍。
- **三种排法**：
  - A 现在的：`人设 + 世界设定 | 制作人（含时间、好感度）+ 记忆 + 参考资料 + 格式说明`（一条系统消息）→ 历史 → 这句话。
  - B：`人设 + 世界设定 + 格式说明 | 制作人档案那几项（称呼、性别、生日日期）`（一条系统消息）→ 历史 → 靠后的系统消息（时间、好感度、记忆、参考资料或预先回忆的剧情）→ 这句话。历史里不留之前的动态内容。
  - C 只追加：同 B，但之前每回合的那条动态系统消息都留在历史里，放在它那回合用户的话前面。
- **工具**：
  - 排法那组每回合照常提供工具、允许调用。
  - 工具那组：第 4、7 回合换成问往事的话，动态内容里带上预先回忆的剧情。这两回合分别「不提供」（drop）、「提供并 `tool_choice: none`」（none）、「照常允许」（auto）。调了工具以后的第二轮也用同一种方式。DeepSeek 在 B 和 C 上各测了一遍，其他模型只测了推荐的 B（Gemini 只在 C 上测过）。
  - 工具回合另测：取同一排法那段对话的前 5 回合作历史，第 6 回合问往事、不预先回忆，让模型自己调工具。答上剧情以后，第二轮分别用 none 和 auto。

## 结论

### 排法

**DeepSeek（`deepseek-flash`）**

| 排法 | 命中率 | 去掉第 1 回合 | 10 回合未命中合计 | 输入花费（闲时价） | 第 10 回合的提示词 |
|---|---|---|---|---|---|
| A 现在的 | 62.3% | 69.1% | 36,958 | $0.00573 | 9,367 token |
| B 靠后的系统消息 | 75.2% | 83.3% | 24,480 | $0.00389 | 9,540 token |
| C 只追加 | 86.0% | 91.2% | 23,309 | $0.00392 | 22,781 token |

**B 比 A 好多少：输入花费少 32%。** 去掉第 1 回合的命中率从 69% 升到 83%。

- A 每回合只命中开头 6,784 个 token，也就是人设和世界设定那段，历史一个字都接不上。
- B 从第 3 回合起，每回合只有几百到两千多个 token 未命中：这回合的动态内容、这句话和上一回合的回复。
- B 在 DeepSeek 上能接上历史，靠的是 DeepSeek 会把几次请求共有的开头单独存成一个缓存单元（`research.md` 1.4）。上一回合和这一回合的请求，共有「开头 + 到再上一回合为止的历史」这一段。

**C 比 B 好多少：命中率高 8 个点，但几乎不省钱。**

- 未命中的 token 差不多：10 回合合计少 5%，每回合差几十到几百个。花费 $0.00392 对 $0.00389。
- 命中率高，主要是因为分母大了。C 把每回合的动态内容都留在历史里，10 回合下来总输入多 68%。第 10 回合的提示词是 B 的 2.4 倍（22,781 对 9,540 token），之后平均每回合再多约 1,300 token。
- 按票 04 的分段截断（N = 20 时带 20 到 29 回合），C 每次请求会多带 20 到 29 份旧的时间、好感度、记忆和参考资料，估计多 2.6 万到 3.8 万 token。
- C 在 DeepSeek 上也没能完全接上：每回合只接到上一回合输入的末尾，上一回合的回复照样未命中，和 B 一样。**推断**原因是开着思考时，DeepSeek 存下的「输出末尾」单元里带着思考内容，而历史里发回去的只有回复，两者对不上。

**换别家看站不站得住**

去掉第 1 回合的命中率（括号里是 10 回合未命中合计）：

| 模型 | A | B | C | C 第 10 回合提示词是 B 的几倍 |
|---|---|---|---|---|
| deepseek-flash | 69.1%（36,958） | 83.3%（24,480） | 91.2%（23,309） | 2.4 |
| mimo-v2.6-flash | 47.5%（57,506） | 75.2%（32,372） | 91.6%（23,369） | 2.4 |
| qwen3.8-flash | 70.6%（36,471\*） | 80.0%（28,260） | 81.5%（27,573\*） | 2.2 |
| gemini-3.8-flash | 0%（6 秒和 20 秒各一遍） | 0%（同左） | 22–26%，只在最后两三回合命中 | 2.4 |
| qfmodel | 0% | 0% | 0% | 2.3 |

\* qwen 的 A、C 各有一回合模型自己调了工具，第二轮用 `none` 时全部未命中（见下文「工具回合的第二轮」）。这里扣掉了那两轮：A 扣 10,232，C 扣 14,070。扣之前分别是 46,703 和 41,643。

- **mimo 和 qwen 的规律和 DeepSeek 一样。** A 每回合只命中开头那一段（mimo 6,144，qwen 7,168），B 能接上大部分历史。
  - mimo 的 B 第 2 回合整个没命中，从第 3 回合起才接上；它似乎要见过两次共同的开头才存下来（**推断**）。B 比 C 多出的 9,000 个未命中几乎都在这一回合，第 3 回合以后两者每回合的未命中差不多。
  - qwen 按 1,024 个 token 一块命中，B 的历史命中一块一块往上涨，所以 B 和 C 差得更小。
- **Gemini 的缓存规律弄不清，也不稳定。**
  - 它会缓存：同一个请求原样连发三次，第 2、3 次命中 7,396 / 9,438。但即便原样重发，也只命中一部分。
  - 对话里，A 和 B 一次都没命中过（加起来 63 次请求，包括单独重跑的 20 秒间隔那遍），连开头的人设和世界设定都没命中。
  - C 只在提示词长到 2 万 token 上下以后才偶尔命中，而且时有时无，比如 20 秒那遍第 10 回合又是 0。
  - 第一遍 20 秒间隔是和 Gemini 的工具那几组同时跑的，后来单独重跑了一遍，结果一样：A、B 都是 0，C 是 24%。
  - 这家服务后面怎么转发、Gemini 的隐式缓存按什么规则命中，都不知道，所以不再往下推断。
- **qfmodel 只有一模一样的请求才命中**：原样重发时命中 9,556 / 9,562，三种排法下一次都没命中，连 C 都没有。它只在命中大于 0 时才给 `prompt_tokens_details.cached_tokens`，没命中时整个字段都不给，所以表里的「没报」就是 0，和票 01「没报按 0」的口径一致。工具那几组测不出东西，跑到一半就停了。

### 预先回忆过的回合怎么处理工具

**DeepSeek，在 B 上**（推荐的排法）：

| 处理 | 去掉第 1 回合 | 输入花费 | 第 4、7 回合命中 | 第 5、8 回合命中 |
|---|---|---|---|---|
| 不提供（drop） | 82.4% | $0.00401 | 7,296 / 9,855、7,808 / 10,368 | 7,936、8,576 |
| `tool_choice: none` | 82.5% | $0.00399 | 7,296 / 9,853、7,808 / 10,344 | 7,936、8,576 |
| 照常允许（auto） | 83.7% | $0.00459 | 第 1 轮 7,936 / 10,271、8,704 / 10,921，另加一轮 | 8,192、8,960 |

在 C 上的结果是同一个方向（见明细）：drop 85.4%，none 85.5%，auto 91.1%；第 4、7 回合 drop 和 none 都是 9,088 和 13,440。

- 在 DeepSeek 上，none 和 drop 的命中一样：预先回忆过的回合两者相同，其他回合只在两处差 128（B 上第 6、9 回合，C 上第 9 回合），像是偶然。这和 `research.md` 4.1 的推断一致：`tool_choice: none` 时，工具说明整个不渲染。所以这一回合只能接到第一条系统消息的末尾。在 B 上，这一回合比照常允许少命中 640 到 900 个 token；在 C 上少命中 2,700 到 3,100 个。
- 照常允许命中最多，但**模型会再调一次工具**。动态内容里明明已经有那段剧情，模型还是先调 `recall_story`，第 1 轮一个字也不说，答上以后第二轮才开口。这样多了一轮请求，开口晚约 1.4 秒（线上还要加上检索的时间）。所以在 B 上，照常允许反而最贵。
  - DeepSeek：4 次里 4 次（B、C 各 2 次）；
  - Gemini：2 次里 2 次；
  - mimo：2 次里 1 次；
  - qwen：2 次里 2 次。
- **别家的 none 和 drop 不一样**：
  - mimo 用 none 时，这一回合一个 token 都没命中，测到的三次都是；drop 一次 0、一次命中 8,192。
  - qwen 用 none，第 4 回合是 0，第 7 回合 8,192；drop 是 7,168 和 8,192。
  - Gemini 上两者都是 0。

  也就是说，none 从没比 drop 好过，在有的服务上还更差，连开头的系统提示词都接不上（**推断**：这些服务在 `none` 时改动了开头的渲染）。

### 工具回合的第二轮

即调过工具、答上剧情之后的那次请求：

| 模型、排法 | 第二轮用 `none`：命中 / 总输入 | 平均未命中 | 照常允许：命中 / 总输入 | 平均未命中 | 照常允许时又调了工具、一个字没说 |
|---|---|---|---|---|---|
| deepseek-flash，B | 21,888 / 32,691（67.0%，3 次） | 3,601 | 53,888 / 56,819（94.8%，5 次） | 586 | 5 次里 0 次 |
| deepseek-flash，C | 27,264 / 52,219（52.2%，3 次） | 8,318 | 172,928 / 179,184（96.5%，10 次） | 626 | 10 次里 1 次 |
| mimo，B | 0 / 33,733（3 次） | 11,244 | 54,080 / 57,377（94.3%，5 次） | 659 | 5 次里 0 次 |
| qwen，B | 0 / 34,948（3 次） | 11,649 | 10,752 / 11,804（1 次，之后额度用完） | 1,052 | 1 次里 0 次 |
| gemini，C | 0 / 51,654（3 次） | 17,218 | 73,279 / 86,872（84.4%，5 次） | 2,719 | 5 次里 0 次 |

- **用 `none`，在所有模型上都接不上第一轮。** DeepSeek 每次都只接到第一条系统消息的末尾（B 7,296，C 9,088）；别家干脆一个 token 都不命中。照常允许则几乎全部命中。
- 在 DeepSeek 上，每个工具回合用 `none` 要多出约 3,000 个未命中 token（B），按闲时价约 $0.00045；在 C 上多约 7,700 个，约 $0.0012。
- 照常允许的代价：一共 31 次（DeepSeek 15 次、Gemini 10 次、mimo 5 次、qwen 1 次）里，有 1 次模型又调了一次工具，一个字没说（DeepSeek，查「1stLIVE 初めてのライブ デビュー」）。引擎里这一轮已经是最后一轮，这个调用不会有人理，回合就以「对话模型没有返回任何内容」失败。
- Gemini 那组的脚本，起初没像产品的适配器那样，把 Gemini 的思维签名（`extra_content`）随调用发回去。补上以后重跑，这家的流里根本没有签名，结果也一样：用 `none` 3 次都是 0，照常允许命中 67.5%。

## 推荐（交给用户定）

**Q5 排法：推荐 B。**

- 缓存规律正常的三个模型上（DeepSeek、mimo、qwen），从 A 换到 B，能省下的大头都省下了：10 回合未命中分别少 34%、44%、23%。
- 从 B 再换到 C，多省的很少：DeepSeek 少 5%；qwen 差不多；mimo 少 28%，但几乎全是第 2 回合那一次，对话越长越不显眼。线上的 DeepSeek 上，B 和 C 花费持平。
- C 的代价：
  - 提示词随对话越来越长：第 10 回合已是 B 的 2.2 到 2.4 倍，截断以后还要多带 20 到 29 份旧的动态内容。
  - 模型每回合都要读一堆过时的「现在是几点」、旧的好感度感受、旧的记忆，角色表现走样的风险更大。
  - 票 04 还得为每回合存下当时的动态内容。
- B 的风险：在 Gemini 这类规律不明的服务上，B 和 A 一样一次都不命中，只有 C 偶尔能命中，而且要到 2 万 token 以后、时有时无。qfmodel 上三种排法都不命中。这只影响自带 LLM 的用户和换服务的部署者，不影响线上现在的花费。
- Anthropic 按设计在历史末尾打断点接上，和排法无关。OpenAI 的自动缓存按文档是按前缀命中，**推断** B 能像 DeepSeek 那样接上，没实测。

**Q9 怎么禁止调用：推荐维持现状。** 预先回忆过的回合和最后一轮都用 `tool_choice: none`，不按服务区分。

- 预先回忆过的回合：照常允许时，模型几乎都会多调一次工具（四个模型 10 次里 9 次），晚开口。通话里，这比省下的几百个命中要紧得多；在 DeepSeek 的 B 上，照常允许甚至更贵。none 和 drop 在 DeepSeek 上一样，在 mimo、qwen 上 none 有时更差。但 drop 每回合工具时有时无，正是票 02 要去掉的情况：引擎的注释写着，有的模型工具一变就丢掉之前的思考；OpenAI、Anthropic 官方也建议用 `none` 而不是删工具。按 ADR-0019，不为个别服务换发法。
- 工具回合的第二轮：照常允许在 DeepSeek 的 B 上，每个工具回合只省约 $0.00045，却有大约 3% 的回合会失败（31 次里 1 次）。真要拿这笔钱，得加一条退路：「第二轮又只调工具时，再用 `none` 补发一次」。这样回合更复杂，偶尔更慢，不值。
- 所以票 04 在禁止调用上不用改代码。
