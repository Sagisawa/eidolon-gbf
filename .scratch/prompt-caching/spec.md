# 提示词缓存：看得见命中率，让对话模型的输入多命中缓存

Status: ready-for-agent

术语以 `GLOSSARY.md` 为准。遵守 ADR-0019（只按协议原样发，不维护各家服务的兼容表）。调研见 `research.md`（各家用量里命中数的字段、价格目录的缓存价、Anthropic 断点、DeepSeek 的工具渲染和中途系统消息）。

## Problem Statement

对话模型每个回合都把人设、世界设定、制作人、这回合找到的记忆和剧情、历史和这句话整个发给服务商。服务商会缓存请求的开头，下次开头一致的部分按缓存价收：线上用的 `deepseek-flash` 命中价是未命中价的 1/50。

现在的问题：

- **看不见。** 适配器只记总输入和输出，服务商报的命中数丢掉了；看板按普通输入价估算花费，看不出缓存省了多少，也没法验证改动有没有效果。2026-10-13 DeepSeek 控制台的数字是命中 64 万、未命中 28 万、输出 12 万（不全是本项目的），命中率约 70%，只能去控制台看。
- **每回合变的内容排在历史前面。** 系统提示词里制作人那段带着精确到分钟的当前时间，后面又跟着这回合的记忆和剧情，所以命中最多到「人设 + 世界设定」为止：历史一个字都命不中，而它正是随对话变长的那部分。通话里回合最密，浪费最多。
- **历史窗口每回合挪一格。** 只带最近 N 回合，超过后每回合丢掉最早的一回合，就算动态内容挪走了，长对话的历史开头也每回合都变。
- **工具时有时无。** 这回合已经预先回忆过剧情就不提供回忆工具；工具定义排在历史前面（DeepSeek 接在第一条系统消息后，OpenAI、Anthropic 排在最前），有无一变，后面全部接不上。
- **Anthropic 协议完全不缓存。** Claude 要显式打 `cache_control` 才缓存，我们没打。

## Solution

1. 每次 LLM 调用记下命中缓存的输入 token；价格多一项缓存命中价；看板显示每个模型的命中率，花费按缓存价估算。
2. 回忆工具每回合都提供；预先回忆过剧情的回合和最后一轮一样「提供但禁止调用」。
3. Anthropic 协议在所有用户共用的固定部分末尾打缓存断点；动态内容挪走以后，再在历史末尾打一个。
4. 用一个一次性实验，在 `deepseek-flash` 上实测几种排法和几种禁止调用的方式各命中多少，用户据此定下第 5 条的形式和 DeepSeek 上怎么禁止调用。
5. 每回合变的内容（当前时间、好感度、生日当天的提醒、找到的记忆、预先回忆的剧情和参考资料）挪到历史后面，作为靠后的第二条系统消息；格式说明挪进共用固定部分。
6. 对话模型带的历史分段截断：后台设的回合数是下限，攒到下限加一半时一次砍回下限。

## User Stories

1. 作为管理者，我想在看板上看到每个 LLM 的缓存命中率，这样不用去服务商控制台也知道缓存有没有在起作用。
2. 作为管理者，我想让看板的花费按缓存价估算命中的那部分输入，这样估出来的数接近实际账单。
3. 作为管理者，我想在价格页看到并能改每个模型的缓存命中价，这样目录没有或者不对时我能自己填。
4. 作为管理者，一个模型查不到缓存命中价时，我希望命中部分按普通输入价算，宁可估高也不少算。
5. 作为管理者，服务商没报命中数时，我希望当作全部没命中，而不是猜一个数。
6. 作为部署者，我希望价格目录（models.dev、OpenRouter）里有缓存价的模型自动带出缓存命中价。
7. 作为部署者，我想让对话模型的输入尽量命中缓存，这样同样的用量花费更低。
8. 作为部署者，我希望改动以后角色的表现不变：照样知道现在几点、记得用户说过的事、能回忆剧情、按好感度档位说话、生日当天祝福、回应礼物。
9. 作为在通话里的用户，我希望角色开口不比现在慢，命中缓存的话还能更快。
10. 作为用 Claude（Anthropic 协议）的部署者，我希望我的对话模型也能命中缓存，而不是每回合全价。
11. 作为用第三方 Anthropic 兼容服务的部署者或自带 LLM 的用户，我希望加了缓存标记以后请求照样成功。
12. 作为用 Chat Completions 或 Responses 的部署者，我希望发出去的开头和现在一样，不因为这次改动被某些服务拒绝。
13. 作为部署者，我保存一个不接受对话中途系统消息的 Chat Completions 服务时，希望检查当场报错，而不是等用户的回合失败。
14. 作为长对话的用户，我希望角色至少记得后台设的那么多回合，不比现在更健忘。
15. 作为部署者，我希望判断模型、提炼记忆的模型看到的历史和现在一样，不受分段截断影响。
16. 作为维护者，我想先用实测数字决定动态内容怎么排、DeepSeek 上怎么禁止调用，而不是凭推断改提示词。
17. 作为用户（维护者本人），我想读到同一套对话在改动前后的回复对照，自己判断语气和人设有没有走样。
18. 作为自带 LLM 的用户，我的回合也一样记下命中数（看板上仍只显示「自带」），缓存省下的是我自己的钱。

## Implementation Decisions

### 测量（票 01）

- **只记命中，不记写入。** 计量里每次请求多一个数：命中缓存的输入 token，是总输入的一部分。Anthropic 的缓存写入照旧算进总输入、按普通输入价估（比实际少算写入那部分的 0.25 倍，接受）。
- **各协议从哪里读**（详见 `research.md` 第 1 节和「对本项目的含义」）：Chat Completions 读 `usage.prompt_tokens_details.cached_tokens`，没有就读 `prompt_cache_hit_tokens`，再没有就读 `usage.cached_tokens`（Kimi 旧字段），`prompt_tokens` 仍是总数；Responses 读 `usage.input_tokens_details.cached_tokens`；Anthropic 读 `cache_read_input_tokens`，总输入仍是三项之和。都没有就是「没报」，记为空。
- **服务调用表补一列**：命中的输入，可以为空；照现有的启动补列方式加。
- **价格多一项缓存命中价**，可以为空，和输入价同币种、同单位。来源顺序不变：管理者设定的 → 目录的 → 预设的。models.dev 取 `cost.cache_read`；OpenRouter 取 `pricing.input_cache_read`（每 token，乘一百万，和输入价一样处理）。预设里能从官方价格页查到的补上（DeepSeek、Anthropic、OpenAI 等），查不到的留空。价格页能看到、能改这一项。
- **估算**：输入花费 =（总输入 − 命中）× 输入价 + 命中 ×（缓存命中价，没有就用输入价）。没报命中数的按 0。
- **看板**：用量里多一个命中数；LLM 的每一行显示命中率 = 命中 ÷ 总输入（命中没报的调用按 0 计入）。
- 自带密钥的调用照样记命中数，看板照旧只显示「自带」。

### 回忆工具始终提供（票 02）

- 有检索时每回合都提供回忆工具；这回合已经预先回忆过剧情时，和最后一轮一样「提供但禁止调用」（`forbid_calls`）。模型硬调了照旧不理。
- 已知局限：按 DeepSeek 开源编码器，`tool_choice: none` 时工具说明整个不渲染，等于没提供，所以在 DeepSeek 上这一条可能没有收益（甚至每个工具回合的第二轮都接不上第一轮）。这由票 03 实测，票 04 按结果定；在那之前按 OpenAI、Anthropic 官方建议的做法（保留工具、用 `none`）。

### Anthropic 缓存断点（票 02 打第一个，票 04 打第二个）

- 引擎发出的开头系统内容拆成两条系统消息：**共用固定部分**（人设、世界设定；票 04 起再加格式说明），同一位角色同一天对所有用户都一样；**其余部分**。
- Chat Completions 和 Responses 把开头连续的系统消息用空行拼成一条（和现在发出去的文本逐字相同）；Anthropic 把它们变成 `system` 的文本块数组，在共用固定部分那块打块级 `cache_control: {"type": "ephemeral"}`，不带 `ttl`（5 分钟）。不用顶层 `cache_control`：Kimi 之外的第三方大多没写支持，和块级混用还可能 400。
- 第二个断点（票 04）打在历史最后一条消息上，让下一回合从这里接上。断点最多 4 个，我们用 2 个。

### 实验（票 03）

- 一次性脚本，不进产品代码，放在 `.scratch/prompt-caching/` 下。用本地 `.env` 里部署者的 DeepSeek key 直接调 `deepseek-flash`，用真的人设、世界设定和格式说明拼提示词，记忆、剧情用大小相近的假内容；每种情况跑一段 10 回合左右的固定对话，记每回合的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。用户已同意花费（预计不到 $0.05）。
- 比较三种排法：现在的；动态内容作为靠后的系统消息放在这句话前面（历史里不留）；只追加（每回合的动态内容留在之后发出的历史里）。
- 比较三种工具处理：不提供；提供并 `tool_choice: none`；照常允许调用。另测一个调了工具的回合，第二轮用 `none` 和用允许调用时各命中多少；照常允许时模型会不会只调用不说话。
- 结果写成表，附结论，交给用户定：排法用哪种（Q5）、DeepSeek 上怎么禁止调用（Q9）。

### 动态内容后移（票 04，形式按票 03 的结果）

- **固定在前**：共用固定部分（人设、世界设定、格式说明），然后是这位制作人的资料（称呼、性别、生日日期），然后是历史。
- **靠后**：当前时间、生日当天的提醒、好感度那几行、找到的记忆、预先回忆的剧情和参考资料，合成一条系统消息，放在历史后面、这句话前面。对话事件的旁白照旧放在用户的话前面。
- **各协议怎么发**：Chat Completions 原地发 `role: system`（`deepseek-flash` 的编码器把中途系统消息渲染成独立一段）；Responses 原地发一条 system 角色的输入项，不再拼进 `instructions`；Anthropic 不发系统消息（中途系统消息只有较新的 Claude 支持，第三方多半不认），改成用户这一轮最前面一个独立的文本块。
- **保存时的检查**（`check_chat_llm`）发的请求里也带一条靠后的系统消息，和真实回合同形，不接受的服务当场报错。
- 若票 03 选了「只追加」：每个回合记下当时带上的动态内容，之后的回合在历史里原样带上；它属于发给模型的内容，不显示给用户，也不进对话记录的接口。具体存法在票 04 定。
- 改完写 ADR：每回合变的内容为什么放在历史后面、为什么用系统消息、Anthropic 为什么例外。

### 历史分段截断（票 04）

- 后台的「带上的历史回合数」N 是下限，步长取 N 的一半（向下取整，至少 1）。总回合数 T 不超过 N 时全带；超过时从开头砍掉 步长 × ⌊(T − N) ÷ 步长⌋ 回合，所以带的回合数总在 N 到 N + 步长 − 1 之间，每过一个步长才变一次开头（N = 20 时带 20 到 29 回合）。截断点只由回合数算出，不存状态。N 为「不限」时全带。
- 只用在对话模型的提示词上；检索判断、好感度判断、提炼记忆照旧只看最近 N 回合。

## Testing Decisions

好的测试只看外部行为：发出去的请求长什么样、记下了什么、看板和估算给出什么数，不看内部怎么拼。三处接缝，都已有先例：

- **LLM 适配器的线路接缝**（假的 HTTP 传输，看请求体、喂流式响应）：先例 `test_llm_protocols.py`、`test_openai_compat.py`、`test_llm_effort.py`。测命中数从各种字段读出、没报为空；开头的系统消息在 Chat Completions / Responses 上拼成一条且文本不变；Anthropic 的文本块和断点位置；靠后的系统消息在三种协议上各自的形状。
- **对话引擎接缝**（假的 ChatLLM 记下收到的消息和工具）：先例 `test_turns.py`、`test_recall_story.py`、`test_conversation_history.py`、`test_producer_profile.py`、`test_affinity_prompt.py`。测预先回忆过的回合也提供工具且禁止调用；两条开头系统消息的内容；动态内容在历史之后；连续两个回合发出的消息里，前一回合的开头是后一回合的开头（缓存能接上的直接判据）；分段截断在各个回合数下带了哪些回合；判断和记忆看到的历史不变。
- **运行记录和看板接缝**（真的 `ActivityLog`、临时库）：先例 `test_activity_records.py`、`test_service_call_models.py`、`test_cost_estimate.py`、`test_price_catalog.py`。测命中数记下、旧表补列；目录读出缓存价；估算按缓存价、缺价按输入价、没报按 0；看板命中率。
- 前端只测纯函数：先例 `adminPrices.test.ts` 和看板的纯函数测试。
- 实测：本地构建版接真实 `deepseek-flash`，同一位角色连发几个回合，看板命中率随回合上升。票 04 另有改动前后的对照稿，由用户读。

## Out of Scope

- 缓存写入的记录和写入价（Anthropic 的 1.25 倍）。
- DeepSeek 的高峰价、长上下文分档价、OpenRouter 在用量里直接给的花费。
- 1 小时有效期的缓存。
- 判断模型、提炼记忆模型、向量化、重排的缓存优化（提示词短，意义不大）。
- 输出侧的花费（线上输出占六成，思考强度和提炼记忆的输出长度是另一回事）。
- 按服务商区分发法的兼容表（ADR-0019）。
