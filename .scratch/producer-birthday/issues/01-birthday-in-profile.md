# 01: 档案能存生日

**What to build:** 制作人档案加一项生日，只有月和日。用户可以通过档案接口保存、清空、读回生日，换一台设备登录也是同一个生日。填了生日后，角色平时就知道它：问「我生日是几号」能答上来，但不会主动提起；如果记忆里的说法和档案不一样，以档案为准。没填生日时，提示词里什么都不写。

这一票不做生日当天的祝福（02），也不做设置页（03）。验证都通过接口和提示词测试完成。见 spec「Implementation Decisions」的存储、接口、提示词三条。

**Blocked by:** None (can start immediately)

**Status:** resolved

- [x] 档案接口多了 `birthday` 字段（`{"month", "day"}` 或 `null`），保存后读回一致；它跟着用户走，换一个客户端读也一样，别的用户读不到。
- [x] 漏掉 `birthday` 或者传 `null` 都会清空生日，和其他几项的规则一样。
- [x] 2 月 29 日可以保存；2 月 30 日、4 月 31 日、13 月、0 日、只有月没有日，都返回 422，原来的档案不变。
- [x] 已有档案的旧库（档案表没有生日两列）启动后会自动补上这两列，原来的称呼、性别、时区照旧，生日为空。
- [x] 填了生日后，提示词的「# 制作人」这一节写着生日是几月几日，并写明这是制作人在档案里填的、和记忆不一致时以档案为准、平时不主动提起。
- [x] 没填生日时，提示词里没有任何关于生日的内容。
- [x] 删除用户时，生日随档案一起删掉（现有的删除测试仍然通过，必要时补一条断言）。
- [x] 后端测试都写在制作人档案的测试文件里，沿用「经 HTTP 接口读写档案、发起回合、检查假 LLM 收到的系统提示词」的做法。

## Comments

实现在 0ce870a。全部验收项都由后端测试覆盖（`tests/test_producer_profile.py`），没有需要人工看的界面。

code-review（固定点 b4d79dd）之后修正了：

- 测试按 CODING_STANDARDS「Holds by construction」「Parameters that don't branch」删减：「只有月」「日为 null」是 pydantic 自己回的 422，删掉；2 月 30 日和 4 月 31 日走同一个上界判断，留 2 月 30 日；「漏掉」和「null」清空是同一条路，只留 null。生日的保存读回并进原来「档案跟着用户走」的测试，用 2 月 29 日，顺带覆盖闰日可以保存。删除账号的测试不再另加生日断言（整行删除，必然成立）。
- 「没填生日」的断言改成「制作人的生日」不在提示词里，免得以后角色资料（如真乃的生日）被检索进提示词时误报。
- 旧表补列抽成 `Store._add_missing_columns`，users 表和档案表共用。

没改的：数据库层没有「两列要么都有要么都空」的 CHECK，只在接口层保证，读的时候缺一列就当没填；接口没开 pydantic 严格模式，`"5"` 这种写法也会被接受。

注意：设置页（票 03）做完之前，在现有设置页保存档案会把生日清空（前端还不发 `birthday`）。
