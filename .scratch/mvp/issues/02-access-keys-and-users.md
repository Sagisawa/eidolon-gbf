# 02: 访问密钥与用户

**What to build:** 引入用户和访问密钥。管理员通过命令行为某位用户签发访问密钥，也可以吊销；一位用户可以持有多把密钥。用户在设置页填入密钥后才能对话，对话记录归属到这位用户。记忆、档案、对话记录都挂在用户上，而不是挂在密钥上（见 `CONTEXT.md` 中的「访问密钥」）。

**Blocked by:** 01

**Status:** resolved

- [x] 管理员可以通过命令行创建用户、为用户签发访问密钥、吊销某把密钥
- [x] 没有密钥、密钥无效或密钥已被吊销时，后端接口拒绝请求，前端显示明确的提示
- [x] 同一位用户的两把密钥访问的是同一份对话记录
- [x] 吊销一把密钥后，该用户的数据不受影响，用另一把密钥仍然可以访问
- [x] 设置页可以填入并保存访问密钥（保存在浏览器本地）
- [x] 移除 01 中的默认用户，所有请求都根据访问密钥确定对应的用户
- [x] 以上行为都有通过后端对外接口驱动的测试

## Comments

**实现完成（分支 `claude/vibrant-gauss-gz0etz`）**

- 数据：新增 `access_keys` 表（`id`、`user_id`、`secret_hash`、`revoked_at`），只存密钥的 SHA-256；`users` 新增唯一的 `name`。旧库自动迁移，01 的默认用户保留为名为 `default` 的用户。
- 管理命令：`eidolon user create|list`、`eidolon key issue|list|revoke`（`--db` 可指定数据库）；`eidolon` 不带参数仍然启动服务。密钥形如 `esc_…`，只在签发时显示一次，之后按 8 位编号管理。
- 接口：除 `/api/health` 外都要求 `Authorization: Bearer <密钥>`；缺失、无效、已吊销分别返回带中文说明的 401。访问别人的对话一律 404。
- 前端：`/settings` 把密钥保存到 localStorage；所有请求都带上密钥，`/api/*` 转发时一并转发；对话页遇到 401 显示原因和「前往设置」链接。
- 测试：`tests/test_access_keys.py`，通过命令行和后端接口驱动；原有测试改为用命令行签发的密钥访问。
