# 08: 剧情目录与「回顾剧情」工具

**What to build:** 导入剧情时同时生成按「角色 → 卡或活动 → 话」分层的剧情目录。对话引擎支持 LLM 工具调用，并接入「回顾剧情」工具：用户问「那次拍写真集是怎么回事」这类概括性问题时，角色通过这个工具从剧情目录找到对应剧情，再据此回答。这个工具对应参考项目的 `recall_streams`。

**Blocked by:** 07

**Status:** resolved

- [x] 对话引擎支持工具调用的完整往返：模型发出调用 → 执行工具 → 把结果交回模型 → 生成最终回复

- [x] 测试：假 LLM 按剧本发出「回顾剧情」调用后，最终回复所依据的内容来自剧情目录

## Comments

实现摘要：

- 剧情目录（`StoryCorpus.catalog(character_id)`）：直接从剧情库的 `episodes` 和 `episode_cast` 表查询生成，按「角色 → 卡或活动（`CatalogSource`：分类、出处）→ 话（`CatalogEntry`：来源标识、标题）」分层。卡或活动按其第一段剧情的来源标识排序，话按来源标识排序（即游戏里的编号顺序）。没有另建一张表：导入写入剧情时目录就随之更新，重复导入、改名、失败结局被移除后都自动正确。导入命令结束时会打印每位角色的目录规模。
- 工具调用：`ChatLLM.stream(messages, tools)` 现在依次产出文字片段和完整的 `ToolCall`；`ChatMessage` 新增 `tool` 角色、`tool_calls` 和 `tool_call_id`。OpenAI 兼容适配器按 `index` 拼接流式的工具调用片段，缺 id 时补上 `call_<index>`，参数不是 JSON 对象时交给引擎报参数错误。
- 对话引擎：配置了检索时向对话模型提供「回顾剧情」工具（`recall_story`，参数 `query`）。模型发出调用 → 引擎执行 → 把 assistant 的调用和 tool 结果追加进提示词 → 再次请求，最多 2 轮（`MAX_TOOL_ROUNDS`），最后一轮不再提供工具，此时即使模型仍发出调用也不会执行。模型在调用工具前说的话也算回复的一部分（语音会先读出来）；对话记录只保存最终回复，不保存工具往返。未知工具、参数错误、检索出错都以文字结果交回模型，回合照常完成。
- 「回顾剧情」（`Retrieval.recall_story`）：把 query 向量化，只在当前角色出场过的剧情中检索片段，用重排选出分数不低于 0.3 的最多 2 段剧情，返回每段剧情的「分类 / 卡或活动 /「标题」」、同一张卡或同一个活动中她出场的其他剧情（来自剧情目录），以及剧情的台词（最多 3000 字）。找不到时明确告诉模型没有经历过、不要编造。和 Jev 的判断无关，由对话模型自己决定是否调用。
- 测试：`test_story_import.py`（切入点 B）覆盖目录层级、重复导入、新增剧情、改名后的目录；`test_recall_story.py`（切入点 A）用假 LLM 按剧本发出调用，验证最终回复依据的工具结果来自剧情目录和剧情库、恋鐘查不到真乃的剧情、没有检索时不提供工具、调用前的话进入回复、轮数上限、异常调用；`test_openai_compat.py` 用录制的流验证工具调用的拼接、并行调用、回传格式。

- 工具结果目前是剧情原文节选，不是摘要；如果实测太长或太慢，可以在导入时用后台模型为每段剧情生成摘要。

真实服务验证（2026-09-25，对话模型 deepseek-v4.1-flash，经 OpenAI 兼容接口；Jev、硅基流动均为真实服务；剧情库为完整导入的 SCTranslationData）：

- 导入：重复导入完整剧情库时没有重新向量化，耗时约 4 秒。目录规模：真乃 120 张卡或活动、445 段剧情；恋鐘 112 张卡或活动、341 段剧情。
- 该不该调用：3 句闲聊（早上好、今天好累、最喜欢吃什么）都没有调用；5 句「那次……」式的问题都调用了，查询词由模型自己改写成日语概括（如「W.I.N.G. 決勝」「公園で鳩と一緒に歌った」）。
- 调用前会不会先说话：这个模型每次都是直接调用，调用前没有输出文字。所以语音通话里，用户在工具轮次期间会一直听不到声音。
- 内容：回答都基于工具返回的剧情。真乃讲出了公园唱歌时被搭话、先拒绝后答应的经过；恋鐘讲出了「長崎よかとこ」里逛长崎展销会、买特产的经过。问恋鐘真乃的公园剧情时，第一次调用返回「没有想起」，模型又换两个查询词试了一次，其中一个查到一段不相关的 G.R.A.D. 剧情；最终她还是坦率地说不记得和鸽子唱过歌，没有冒认。
- 调用轮数：模型有时一轮发出 2 个并行调用，有时用满 2 轮（一次问 W.I.N.G. 决赛时共调用 4 次）。
- 延迟：这是最大的问题。不调用工具时，首个字幕约 5–9 秒。调用工具时首个字幕约 20–32 秒，分解如下：
  - 这个模型每一轮的首 token 就要 3–4 秒以上（直接测适配器：首个片段 3.65 秒，之后 1 秒内输出完）；
  - 回合开头 Jev 判断需要检索时，还会先做一次检索（约 4 秒）；
  - 每次工具执行约 1–4 秒（硅基流动向量化和重排冷启动各约 2 秒，热了以后合计约 1.2 秒）；
  - 工具回合至少要请求模型两次。
- 其他发现：
  - 目录里有文件名就是剧本编号的剧情，标题会显示成「produce_events_100100002」「_试镜前④」这样，这是 SCTranslationData 本身的命名；
  - 试镜类剧情（`produce_communication_auditions/…`）的编号排在 `produce_events/…` 之前，所以在「W.I.N.G.編」里列在最前面；
  - 一次与工具无关的闲聊回复里，模型把 `</ja><ja>…` 写在了 `<zh>` 里面，解析器把这些标签原样留在了字幕中（回复格式的容错问题，与本 ticket 无关）。
