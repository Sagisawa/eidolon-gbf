# 16: 工具轮之后，模型把自己的工具调用标记当成回复输出

**What happened:** 对话模型调用一次「回顾剧情」后，引擎在最后一轮不再提供工具（`MAX_TOOL_ROUNDS = 1`，`engine.py` 里最后一轮 `offered = []`）。deepseek-v4.1-flash 这时如果还想再查一次，就会把它原生的工具调用标记当成普通文字输出。这段文字没有 `<ja>`/`<zh>` 标签，解析器把它整个当成一段日语，于是成了角色的回复（语音通话里还会被读出来）：

```
<｜｜DSML｜｜ calls>
<｜｜DSML｜｜ invoke name="recall_story">
<｜｜DSML｜｜ parameter name="query" string="true">決勝前コミュ 決勝前 ステージ前</｜｜DSML｜｜ parameter>
</｜｜DSML｜｜ invoke>
</｜｜DSML｜｜ calls>
```

## 复现（2026-09-25，ticket 13 的真实服务验证中发现）

- 对话模型 deepseek-v4.1-flash，检索、剧情库都是真实服务；Jev 换成总是回答「不需要检索」的桩，让引擎把工具交给模型。
- 问真乃「W.I.N.G.决赛前你在后台说了什么？请先用回顾剧情工具查一下再回答」。
- Chat Completions 和 Responses 接口各跑一次，最终回复都是上面的标记；Anthropic 接口跑一次，正常回答。
- 第二次请求都正确带上了第一轮的调用和工具结果，所以不是适配器的问题，是模型在没有工具可用时仍然想调用。
- 平时 Jev 会把「那次……」类问题提前回顾，模型自己调用工具的情况不常见，但一旦发生回复就坏了。

## 可能的方向（待定）

- 最后一轮仍然提供工具，但告诉服务不许调用（Chat Completions / Responses 的 `tool_choice: "none"`，Anthropic 的 `tool_choice: {"type": "none"}`），需要扩展 `ChatLLM.stream` 的约定；
- 或者在最后一轮的提示词里明确说明「已经不能再查了，请根据已有结果回答」；
- 或者识别并丢弃这类标记，再重新请求一次。

### 决定（2026-09-25）

- **提示词**：在最后一轮之前给模型的工具结果后面追加一句说明，告诉它已经不能再调用工具了，并要求它不要提到查找。实测有效，定为修法。
- **不加标记过滤兜底**：提示词实测 0/150（两版措辞合计）；泄漏的格式也各不相同，过滤列不全；而且要缓冲回复开头，拖慢首字。
- **`MAX_TOOL_ROUNDS` 保持 1**：多给一轮不能根治（最后一轮照样会漏），还多一次首字延迟。
- **不用 `tool_choice: "none"`**：实测 5/30，基本无效，而且要扩展 `ChatLLM.stream` 的约定。

措辞第二版的实测：「查到了但不相关」场景，Chat Completions 和 Responses 各 30 次，泄漏 0 次（另有 1 次网络超时，与本问题无关）。回复开头出现「記録」「調べ」「ツール」等元信息的次数：第一版 19 次，第二版 0 次。

## Agent Brief

**Category:** bug
**Summary:** 在对话模型最后一次读到工具结果时告诉它不能再调用工具，防止它把工具调用标记当成回复输出

**Current behavior:**
`ConversationEngine.turn` 最多给对话模型 `MAX_TOOL_ROUNDS`（现在是 1）轮工具调用，之后再请求一次，这一次不提供任何工具。如果「回顾剧情」查到的内容答不上制作人的问题，模型会想再查一次；这时没有工具可用，它就把自己原生的工具调用标记（DSML、`<call>…</call>`、`<recall_story>…</recall_story>` 等）当成普通文字输出。解析器把这段没有 `<ja>`/`<zh>` 标签的文字当成日语，它于是成了角色的回复：边生成边推给前端，语音通话里还会被读出来，最后被记进对话记录。用真实 deepseek-v4.1-flash 实测，这种场景下 30 次里漏了 7 次，Chat Completions 和 Responses 接口都会漏。

**Desired behavior:**
模型读到的最后一批工具结果（也就是之后那次请求不再提供工具的那一批）末尾，各追加同一段说明：

> （这一轮不能再调用任何工具了，请现在就回答制作人。上面想起来的内容如果答不上他的问题，就像一时记不清那样自然地说，不要提到查找、工具、记录或剧情库。）

- 这批结果里每一条都要加，包括出错的结果（参数有误、没有这个工具）。
- 如果以后把 `MAX_TOOL_ROUNDS` 调大，只有最后一批结果带这段说明，更早几轮的结果不带。
- 说明只存在于发给模型的请求里，不写进对话记录，不影响记录下来的回复和字幕。
- 这段措辞用真实模型实测过，要原样使用；想改措辞，就得重新做真实服务验证（见验收标准的最后一条）。

**Key interfaces:**
- `ConversationEngine.turn` 的工具循环：它在把工具结果作为 `ChatMessage("tool", …, tool_call_id=…)` 加进提示词时，已经知道下一次请求还提供不提供工具。说明就加在这里。
- 提示词文本按惯例定义成引擎模块里的常量，放在 `MAX_TOOL_ROUNDS` 附近。
- `ChatLLM.stream` 的约定和三个适配器都不需要改。

**Acceptance criteria:**
- [ ] 用 `FakeLLM` 写一个文字回合：模型第一轮调用 `recall_story`。第二次请求里这条工具消息的内容，等于检索返回的结果加上那段说明。
- [ ] 第一轮一次调用多个工具（包括一次调用不存在的工具）时，第二次请求里每条工具消息的末尾都带这段说明。
- [ ] 模型第一轮没有调用工具时，回合只请求一次，提示词里不出现这段说明（行为和现在一样）。
- [ ] 记录下来的回复不包含这段说明，下一个回合的历史里也看不到它。
- [ ] 后端全部测试、lint 和类型检查通过。
- [ ] 真实服务验证：在票面的场景下（检索的判断器总是回答「不需要检索」，`recall_story` 返回一段不相关的剧情，问「W.I.N.G.决赛前你在后台说了什么？请先用回顾剧情工具查一下再回答」），用 deepseek-v4.1-flash 的 Chat Completions 和 Responses 接口各跑至少 15 次，最终回复里都没有工具调用标记。结果记进本票的 Comments。

**Out of scope:**
- 修改 `MAX_TOOL_ROUNDS`。
- 给 `ChatLLM.stream` 加 `tool_choice`，或者改动任何适配器。
- 识别或过滤回复里的工具调用标记，或者缓冲回复开头。
- 判断器已经提前回顾过剧情、根本不提供工具的回合（这时不会漏）。
- 对话历史的长度（ticket 17）。
