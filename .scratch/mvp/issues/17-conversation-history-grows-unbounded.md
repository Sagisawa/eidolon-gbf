# 17: 对话历史不设上限，提示词随对话变长无限增长

**What happened:** 引擎每个回合都把本次对话的全部历史放进提示词（`engine.py` 的 `_prompt` 遍历 `store.list_messages(conversation.id)`，没有截断）。一次对话可以跨越多次语音通话和任意多个文字回合，用户不点「新对话」，历史就一直变长：

- 每个回合的输入 token 随对话长度线性增长，按用户限流（ticket 14）只限制回合数，挡不住单个回合越来越贵；
- 对话足够长时会超出对话模型的上下文窗口，回合直接失败；
- 首个字幕的延迟也会随之变长，语音通话里尤其明显。

**Blocked by:** —

**Status:** resolved

## 背景（2026-09-25，ticket 14 讨论单次通话回合上限时发现）

单次通话的回合上限（`EIDOLON_TURNS_PER_CALL`，默认 40）控制的是一次通话的花费，和上下文长度无关：同一个对话里连着打几次通话、再发文字，历史会累加。所以上下文的问题要在引擎里单独解决。

## 可能的方向（待定）

- 只带最近 N 轮，或按 token 预算从后往前取历史；更早的内容靠记忆（ticket 10）和检索接上，这与「新对话只靠检索到的记忆接上以前聊过的事」的设计一致。
- 截掉的部分是否需要一段摘要。spec 里写了「不带上次对话的摘要」，那是针对跨对话的；同一对话内要不要摘要需要决定。
- 上限用回合数还是 token 数；token 数要按对话模型估算，三种接口的计数方式不同。

### 决定（2026-09-26）

- **按回合数截断，不按 token**：只把最近 N 个回合（制作人一句 + 角色一次回复算一个回合）放进对话模型的提示词。token 数要按三种接口分别估算，不值得。
- **不做摘要**：每个回合结束后后台模型都会抽取记忆（ticket 10），截掉的回合里制作人说过的事已经记下，可以被检索接上；这和 spec「不带上次对话的摘要」一致，同一对话内也不另做摘要。
- **默认 20 个回合**，环境变量 `EIDOLON_HISTORY_TURNS` 可调，0 表示不限制（和其他上限的约定一致）。
- 现状核对：只有对话模型的提示词不设上限；记忆抽取（`EXCHANGE_HISTORY = 4`）和检索判断（`JUDGE_HISTORY = 4`）本来就只看最近 4 条消息。

## Agent Brief

**Category:** enhancement
**Summary:** 对话模型的提示词只带本次对话最近 N 个回合的历史

**Current behavior:**
`ConversationEngine.turn` 每个回合都把 `store.list_messages(conversation.id)` 的全部消息放进提示词。对话跨多次通话和文字回合不断变长，输入 token、首字延迟随之线性增长，最终会超出对话模型的上下文窗口，回合直接失败。

**Desired behavior:**
- 提示词里的历史只保留最近 N 个回合，更早的消息不发给对话模型；N 默认 20。
- 截断后的历史必须从制作人的消息开始（Anthropic 接口要求 user / assistant 交替、以 user 开头），不能以角色的回复开头。
- N 由环境变量 `EIDOLON_HISTORY_TURNS` 配置：不设为默认值，0 为不限制，其他非负整数以外的值启动时报错（沿用 `_limit`）。
- 对话记录本身不变：消息接口仍返回全部消息，前端照常显示完整对话。
- 不加摘要，不改记忆和检索。

**Key interfaces:**
- `ConversationEngine.__init__` 接收历史回合上限；`create_app` 从 `Settings` 传入。
- `Settings` 新增字段，`Settings.from_env` 读取 `EIDOLON_HISTORY_TURNS`。
- 截断在引擎读取历史之后、组装提示词之前进行；检索判断和记忆抽取拿到的是截断后的历史（它们本来只看最近 4 条，不受影响）。

**Acceptance criteria:**
- [x] 对话已有超过 N 个回合时，下一回合发给对话模型的提示词里只有最近 N 个回合的历史，加上系统提示和本回合的输入。
- [x] 截断后的第一条历史消息是制作人的消息。
- [x] 回合数不超过 N 时，提示词和现在一样。
- [x] 上限设为不限制时，全部历史都在提示词里。
- [x] 消息接口仍返回对话的全部消息。
- [x] `EIDOLON_HISTORY_TURNS` 的读取：不设为 20，0 为不限制，非法值报错。
- [x] README、`.env.example`、`docs/deploy.md`（如列有环境变量）说明新变量。
- [x] 后端全部测试、lint 和类型检查通过。

**Out of scope:**
- 按 token 预算截断、同一对话内的摘要。
- 在数据库查询里限制读取的消息条数（性能优化，现在的数据量不需要）。
- 修改记忆抽取或检索使用的历史长度。

### 实现（2026-09-26）

- `engine.py` 新增 `latest_turns(messages, turns)`：从倒数第 `turns` 条制作人消息开始保留（`None` 时从第一条制作人消息开始），所以发给模型的历史总以制作人开头；开头如果有没对上制作人消息的角色回复，也会去掉。`ConversationEngine` 新增参数 `history_turns`，读取历史后先截断，再交给检索判断、提示词和记忆抽取。
- `config.py`：`DEFAULT_HISTORY_TURNS = 20`，`Settings.history_turns`，`history_turns_from_env()` 沿用 `_limit`（不设为 20，0 为不限制，非法值报错）；`create_app` 把它传给引擎。
- README、`.env.example` 说明了 `EIDOLON_HISTORY_TURNS`；生产和开发的 compose 都用 `env_file: .env`，不需要另外改。`docs/deploy.md` 没有逐个列出限流变量，没有改。
- 测试 `test_conversation_history.py`（走文字回合接口 + `FakeLLM`）：超过上限只带最近 N 个回合；未超过时和原来一样；不限制时全部带上；默认 20；消息接口仍返回全部消息；`latest_turns` 以制作人开头；环境变量读取。
- 后端 249 个测试通过，pyright 0 错误；ruff 只有原有的两处报错（`corpus.py` E741、`llm/anthropic.py` F401），与本票无关。
- 没有做真实服务验证：改动只影响发给模型的消息条数，三个适配器的格式约定不变。
