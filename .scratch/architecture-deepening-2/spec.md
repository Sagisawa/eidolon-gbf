# 架构加深（第二轮）：作品资料和角色资料的向量化、参考资料来源列表、名单

Status: ready-for-agent

术语以 `CONTEXT.md` 为准；本轮新增了词条「作品资料 (Work Facts)」。设计词汇（module、interface、seam、adapter、depth、locality）取自 `codebase-design` skill。2026-09-28 的架构审查找出 7 个候选，经 grilling 决定做其中两个：向量化文本集和参考资料来源列表（审查里的候选 1），以及名单（候选 2）。候选 3（回合放行）读代码后放弃，理由见同目录的 `grilling-notes.md`。

## Problem Statement

**作品资料的向量化是照着角色资料抄的，已经开始漂移，并且藏住了一个 bug。**
- 作品资料的索引是照着角色资料的索引写的。两者做的是同一件事：文字来自配置文件，第一次检索时向量化，按「文字 + 模型」存进 SQLite，配置改了之后重启只重算改动的条目。
- 实现已经各走各的：作品资料分批向量化、加载后缓存在内存里；角色资料一次全部向量化，每个回合都在事件循环上阻塞地读一遍 SQLite。
- 参考资料有三个来源（剧情、角色资料、作品资料），每个都被逐个点名：`Retrieval` 的构造参数、`rank_references`、`Reference.kind`、提示词里的标题和使用说明、`reembed`、CLI 的 `eval rerank`、`assembly`，一共约十处。加一个来源要把这十处都改一遍。
- 上一次加作品资料时就漏了一处。`eval rerank` 会把作品资料的候选送去重排，但校准集没有作品资料的标签，所以这些候选全被判为「不相关」。现在只要有 `world.json`，rerank 的校准数据就是失真的。

**三个 world sync 导入各有一套「这个名字是谁」的规则，而且彼此不一致。**
- 唱片导入、演出导入和曲目单导入，各自把来源里的人名、声优名、组合名对应到偶像和组合。
- 规范化规则各不相同：有的做 NFKC、有的不做；有的把 `’` 换成 `'`、有的不换；组合读音有的先转成平假名、有的两种都查。
- 结果是，同一个全角写法的组合名，在唱片导入里能对上，在曲目单导入里却进了「对不上」。这不是谁决定的，只是各模块抄了不同版本的辅助函数。
- 要测这些对应规则，现在只能把整套假站点（SPARQL、官方站、Lantis、ふじわらはじめ、CMS、wikiwiki、imas-db）都搭起来。

## Solution

- **先修校准。** `eval rerank` 的校准集可以标注作品资料；报告里剧情、角色资料、作品资料合为「参考资料」一组，共用一个阈值。先跑出一条可信的基线，再做重构。
- **向量化文本集。** 角色资料和作品资料共用一个「向量化文本集」module，所有细节在它里面实现一次：按文字存向量、懒向量化、分批、缓存、遗忘和迁移。角色资料和作品资料的来源只负责提供条目。
- **参考资料来源列表。** 参考资料的来源变成一张列表，每个来源自带 kind、提示词标题和使用说明。`Retrieval`、`reembed`、`eval rerank` 和 `assembly` 都只遍历这张列表，由同一个函数打开。
- **重新向量化 interface。** 剧情库、角色资料、作品资料和记忆四个来源实现同一个很小的 interface，`reembed` 只遍历它们，不再逐个点名。
- **改名。** 代码里的「world index」改为作品资料的名字；提示词标题「资料」改为「作品资料」。
- **名单。** world sync 的三个导入共用一个名单 module，回答三件事：这个名字是哪位偶像、哪个组合、是不是社长或事务员。它只有一套规范化规则。

## User Stories

1. 作为部署者，我想让 `eval rerank` 能标注作品资料的校准问题，这样校准结果反映的是回合里三类参考资料一起重排的真实情况。
2. 作为部署者，我想在 `eval rerank` 的报告里看到剧情、角色资料、作品资料合为「参考资料」一组的分布和阈值命中，这样我能判断 references 阈值对三类来源是否合适。
3. 作为部署者，我想在重构和改名的前后各跑一次 `eval rerank` 并对比，这样我知道重构有没有改变检索的表现。
4. 作为部署者，我想在校准集里的作品资料问题用条目标题作为标签，这样标注直观，不会有歧义。
5. 作为部署者，我想让校准集写错 kind 或引用不存在的标签时，命令报出清楚的错误，这样我不会拿一份写错的校准集得出错误的结论。
6. 作为部署者，我想在升级后第一次启动时不必重新向量化角色资料和作品资料，这样升级不花向量化费用，也不拖慢第一个回合。
7. 作为部署者，我想让我改了角色资料文件或 `world.json` 之后，重启只重算改动的条目，这样行为和现在一致。
8. 作为部署者，我想让配置里删掉的角色资料和作品资料条目，它们的向量也被删掉，这样库里不会越积越多。
9. 作为部署者，我想在换了向量化服务或模型后跑一次 `eidolon reembed`，四类数据都补齐，全部成功后才丢掉旧模型的向量，这样中途失败不会丢东西，重跑能接着做。
10. 作为部署者，我想让 `eidolon reembed` 的日志和报告，仍然分别告诉我剧情库、角色资料、作品资料、记忆各向量化了多少条，这样我能核对进度。
11. 作为部署者，我想让 `eval rerank` 和服务器使用同一套打开参考资料来源的逻辑，这样校准测的就是线上的行为，CLI 也不会漏掉向量缺失的警告。
12. 作为用户，我想让角色在我问到歌曲、唱片或演出时，照样从作品资料里查到并照着回答，这样重构不影响我的体验。
13. 作为用户，我想让角色在回顾经过时，照样把相关的演出和唱片与剧情一起带上，这样重构不影响回忆。
14. 作为用户，我想让回合不因为读角色资料的向量而卡住事件循环，这样同时在线的其他人的回合和通话不被拖慢。
15. 作为角色（经由提示词），我想看到「作品资料」和「角色资料」两个意思分明的标题，这样我不会把作品里的歌、唱片、演出，和关于自己与身边人物的设定混在一起。
16. 作为开发者，我想只在一处添加一个新的参考资料来源（包括它的检索、标题和使用说明），这样不会再漏改某一处。
17. 作为开发者，我想在一处读懂「按文字存向量、懒向量化、分批、缓存、遗忘、迁移」，这样修一个 bug，角色资料和作品资料都一起修好。
18. 作为开发者，我想用一组契约测试覆盖向量化文本集，并对角色资料和作品资料两个 scope 各跑一遍，这样两种用法的行为保证一致。
19. 作为开发者，我想在代码里看到的是作品资料的名字，而不是 world index，这样我不会把它和每次都完整带上的世界设定弄混。
20. 作为部署者，我想让 world sync 对同一个组合名或读音，不论出现在唱片、演出还是曲目单里，都得到同样的对应结果，这样导入报告里的「对不上」都是真的对不上。
21. 作为部署者，我想让 world sync 能认出全角写法、`’` 和 `'` 混用、片假名读音、带空格的声优名这些写法，这样我不必为这些小差异写人工更正。
22. 作为部署者，我想让统一规则之后重跑 world sync 时，`world.json` 和导入报告的每一处变化都能解释，这样我能放心审核 diff 后提交。
23. 作为部署者，我想让事务员和社长照旧不进「对不上的出演者」报告，这样报告只列真正需要处理的条目。
24. 作为开发者，我想直接用表驱动测试验证名单怎么对应名字，不必搭一整套假站点，这样补一个边界情况只要加一行。
25. 作为开发者，我想只在一处读到各导入共用的小工具（取网页的类型、片假名转平假名、去空格），这样不会再抄出第四个版本。

## Implementation Decisions

**校准（最先做，单独一张 ticket）**
- 校准集的问题类型增加作品资料一类，标签是作品资料条目的标题（现有 1431 条，标题互不重复）。
- 报告的分组改为「参考资料」（剧情、角色资料、作品资料，用 references 阈值）和「记忆」（用 memories 阈值）。
- 从 `world.json` 起草约 6 条作品资料的校准问题（歌曲、唱片、演出日各 2 条），交人工审阅后提交。
- 跑一次拿到基线，只报告结果，不改阈值。

**向量化文本集（新的 deep module）**
- 只覆盖「来自配置、按文字存向量」的两类：角色资料和作品资料。剧情库和记忆的存储保持现状。
- 存储：一张表，列为 scope、text、model、embedding，主键是 (scope, model, text)。scope 取 `character:<角色 id>` 或 `work`。
- 迁移：建表时，如果旧的角色资料表或作品资料表还在，就把它们的行一次性复制进新表，再删掉旧表，已有的向量不重算。
- 行为全部在这个 module 内部：
  - 某个 scope 第一次被检索时，读出已存的向量；把配置里有、库里没有的条目分批向量化，每批提交一次；删掉库里有、配置里已经没有的条目。
  - 之后常驻内存。一个 scope 同一时间只加载一次。
  - 读写 SQLite 放到线程里做，不阻塞事件循环。
  - 提供 `forget_other_models`。
- 角色资料和作品资料的来源是它上面的薄 adapter：只提供条目（文字、标题和原对象），以及自己的 scope。

**参考资料来源列表**
- 只管参考资料这一条路（按 Jev 的判断查参考资料时，剧情、角色资料、作品资料一起 rerank）。回顾经过和想起记忆保持各自的规则，不进列表。
- 每个来源提供四样东西：
  - kind，取值为剧情、角色资料、作品资料。作品资料的 kind 由 `"world"` 改为 `"work"`。
  - 提示词里的标题。
  - 给角色的那行使用说明。
  - 按查询向量为某位角色检索候选，返回参考资料条目。
- `Retrieval` 接收来源列表。拼参考资料的提示词只是遍历来源、拼接说明和条目。原来的自由函数 `rank_references` 消失：`eval rerank` 通过同一个来源列表拿到候选和分数。
- 作品资料的来源对外有两种用法：
  - 进列表时不过滤类别。
  - 回顾经过直接调用时，按演出、唱片过滤。
  - `recall_story` 工具仍然只查剧情。
- 一个工厂函数接收数据库路径、embedder、角色和世界设定（可以没有），返回可以一次性关闭的来源列表。`assembly`、`reembed` 和 CLI 的 `eval rerank` 共用它。缺向量的警告也由这里统一发出。

**重新向量化 interface**
- 剧情库、角色资料、作品资料、记忆都实现两件事：
  - 补齐当前模型缺的向量，报告进度，返回条数。
  - 丢掉其他模型的向量，返回条数。剧情库每段只留一份向量，所以恒返回 0。
- 四个来源都在构造时拿到 embedder。记忆为此改为构造时传入 embedder，不再在补齐时临时传入。
- `reembed` 遍历这四个来源，顺序不变：全部补齐成功之后，才统一丢掉旧模型的向量；任何一步失败都不丢。报告仍按四类分别给出条数。

**改名**
- 代码里作品资料的索引和它所在的模块，改为作品资料的名字。`World`（世界设定和原始数据）不动。
- 提示词里的标题「资料」改为「作品资料」，Jev 判断说明里对应的措辞也跟着改。

**名单（新的 deep module，纯 in-process）**
- 由世界设定里的偶像、组合、社长和事务员构造，回答三件事：
  - 一个人名（可以附带声优名）是哪位偶像。去空格，并去掉「（初代）」这类尾注。
  - 一个名字或读音是哪个组合。
  - 一个人是不是社长或事务员。
- 统一的规范化：NFKC，`’` 换成 `'`，去掉非文字字符，casefold。组合的名字和读音都先把片假名转成平假名再比。偶像名和声优名去空格后比，也做 NFKC。
- 留在各导入里的：
  - 从各自来源抽出人名和声优名（Lantis 的「名字（CV:xx）」字符串、wikiwiki 的角色和声优两栏、imas-db title 属性里的「名字(CV:声优)」）。
  - 唱片的特别组合、全員和拆分多人。
  - 演出的「标题行不算人」。
- world sync 在建立名单之前，要在官方组合页和 SPARQL 之间对组合，这一步也改用名单的规范化。
- 曲名比对不纳入名单，保持现状。
- 各导入共用的小工具（取网页的函数类型、片假名转平假名、去空格）收进一个共享的同步小工具模块。把 HTML 拆成行的函数两份标签集合不同，各自保留。

**并行与顺序**
- 校准 ticket 最先做。
- 向量化文本集和来源列表这部分，与名单这部分之间没有 blocking edge，可以在各自的 worktree 并行完成。
- 两者都不改 `CONTEXT.md`。「作品资料」词条已经在拷问中加好。

## Testing Decisions

- 好的测试只经由 interface 断言可以观察到的结果（提示词里出现什么、CLI 输出什么、embedder 被调用几次、库里剩下哪些向量），不检查内部状态。重构内部时，测试不应该需要改。
- 新测试写在新的 interface 上，被它覆盖的旧测试删掉，不在上面再叠一层（replace, don't layer）。

**向量化文本集：契约测试（新的内部 seam）**
- 用临时 SQLite 和 `FakeEmbedder`，对角色资料的 scope 和作品资料的 scope 各跑一遍：
  - 第一次检索时向量化。
  - 再检索不再调用 embedder。
  - 改了一条，重启后只重算那一条。
  - 删掉的条目被遗忘。
  - `forget_other_models` 只留下当前模型的向量。
  - 旧表里已有的向量迁移后不重算。
- 可以参照现有 `test_reembed` 里计数 embedder 调用的写法。

**参考资料和回顾经过：经由回合（现有的最高 seam）**
- `test_world_retrieval`、`test_retrieval`、`test_recall_story` 这类测试经由 `build` 和文字回合 API，只改名字和标题文字。
- 补一条断言：提示词里「作品资料」和「角色资料」两个标题各自对应正确的条目。

**重新向量化：经由 CLI（现有）**
- `test_reembed` 保留，改名字。其中直接构造作品资料索引的那段，由契约测试覆盖后删掉。

**校准：经由 `rerank_eval.evaluate` 和报告（现有）**
- 补作品资料的用例：作品资料的候选按标签判定为相关、可放可不放或不相关；报告的「参考资料」一组包含它们。
- 补错误用例：写错 kind、引用不存在的标签时报错。
- 可以参照现有 `test_rerank_eval`。

**名单：表驱动测试（新的纯 seam）**
- 覆盖：全角组合名、`’` 和 `'`、片假名读音、「三峰結華（初代）」、只有声优名、带空格的声优名、事务员和社长、对不上的名字。

**world sync：经由 CLI 和 `FakeWorldSites`（现有）**
- `test_world_sync` 保留，不需要改。

**真实验收（不是自动化测试）**
- 名单：用真实来源重跑 world sync。`world.json` 和导入报告要么不变，要么每一处变化都能解释；出现意外就停下来讨论。
- 改名：跑一次 `eval rerank` 和基线对比，并用两位角色做一次真实对话验证。

## Out of Scope

- 剧情库和记忆的向量存储方式，不并入向量化文本集。
- 回顾经过和想起记忆的规则，不进参考资料来源列表。
- 调整 references 或 memories 阈值。本轮只报告基线和对比；要不要改，由人看过数据后另行决定。
- 曲名比对的规范化。
- 导入报告由各导入自己写、更正文件只读一次、演出到曲目单的串接（审查的候选 5）。
- 用字典形式的取网页函数逐个测导入。
- 回合提示组装和日期约定（候选 6）、回合事件的对外形式（候选 7）、数据库 module（候选 4）。
- 文字回合的放行（候选 3，已放弃，见 `grilling-notes.md`）。

## Further Notes
