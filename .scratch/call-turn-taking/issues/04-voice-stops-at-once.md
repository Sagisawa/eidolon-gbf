# 04: 打断时声音立刻停下

**What to build:** 通话中角色被打断时，声音要立刻停下。现在从 `InterruptionFrame` 到声音真正停下要 0.9–1.4 秒，见 02 的 Comments 里的真实通话时间线。规则见 `../spec.md` 和 `CONTEXT.md` 的「打断」一条：「角色立刻停止发声」。

**Blocked by:** 02

**Status:** resolved

- [x] 原因（Pipecat 1.11，`pipecat/services/tts_service.py`）：
  - `InterruptibleTTSService._handle_interruption` 在角色说话时（`_bot_speaking` 或 `_tts_started`），会先断开再重连 Fish 的 websocket；
  - `TTSService.process_frame` 要等它做完，才把 `InterruptionFrame` 往下游推；
  - 所以输出端要等重连结束才收到打断，这期间把已缓冲的音频继续播出去；
  - 打断前已经发出的 `delta` 和 `done`（`RTVIServerMessageFrame` 同样经过 TTS）也会晚到约 1 秒。
- [x] 让打断先到达输出端，再重连。可能的做法：
  - 包一层 `FishAudioTTSService`，调整 `_handle_interruption` 的顺序；
  - 或者在 TTS 之后放一个处理器，直接转发打断。
  - 要注意：重连期间如果有新回复的文字送来，不能丢，也不能打到已经关掉的连接上。
- [x] 测试：在 `test_voice_call.py` 的层面（假 TTS），打断之后输出端先收到打断，不必等 TTS 的重连完成。
- [x] 真实通话验证：按 02 的场景再做一次，确认从 `InterruptionFrame` 到客户端静音在几百毫秒以内，`done` 也不再晚到。在 Comments 里记下时间线。

## Comments

### 分诊（2026-09-27）

- **分类 bug**：`CONTEXT.md` 的「打断」要求「角色立刻停止发声」，02 的真实通话测得 0.9–1.4 秒才停，没做到已有的要求。
- **原因已核对**（Pipecat 1.11 源码）：`TTSService.process_frame` 收到 `InterruptionFrame` 时先 `await self._handle_interruption(...)`，再 `push_frame`；`InterruptibleTTSService._handle_interruption` 在 `_bot_speaking or _tts_started` 时先 `_disconnect()` 再 `_connect()`，Fish 的断开还要先发 stop、等 close。02 的 run1 时间线与此一致：28.79 断开，30.16 重连完成，30.17 `BotStoppedSpeakingFrame`。
- **没有现成实现**：通话直接用原版 `FishAudioTTSService`，没有包装。仓库没有 `.out-of-scope/`。
- **给实现者的两点观察**：
  - 处理器按顺序处理帧：打断没处理完，后面的文字帧就在队列里等着。所以只要在同一次处理里改成「先把打断往下游推，再重连」，重连期间的新文字不会丢，也不会打到已关的连接上。
  - `FishAudioTTSService.run_tts` 发现连接已关会自己连上，所以「打断时只断开，下一句要合成时再连」也是一种做法。选哪种由实现者定，但要看断开本身（发 stop、等 close）会不会也拖住打断。

## Agent Brief

**Category:** bug
**Summary:** 通话中角色被打断时，打断先送到输出端让声音马上停下，TTS 的重连放到之后

**Current behavior:**
用户打断正在说话的角色时，`InterruptionFrame` 进入 Fish Audio 的 TTS 服务后，服务先断开并重连 websocket，重连完成后才把打断往下游推。这期间输出端不知道被打断，继续把已缓冲的音频播出去，声音要过 0.9–1.4 秒才停。打断前已经发出、同样要经过 TTS 的服务端消息（回复的 `delta` 和 `done`）也晚到约 1 秒。回复的生成和记录不受影响，它们在打断后约 20 ms 内就已收尾。

**Desired behavior:**
- 打断经过 TTS 服务时，不必等 websocket 断开和重连完成，马上继续往下游传。输出端随即清掉缓冲的音频，客户端在几百毫秒内静音。
- 打断之后的新回复照常合成：重连期间或之后送来的文字不丢，也不会发到已关的连接上；新回复的第一句声音照常出来。
- 被打断的那条回复的音频不会在打断之后漏出来（Pipecat 断开重连本来就是为了丢掉 Fish 那边还没发完的音频，这个效果要保留）。
- 角色没在说话时的打断（例如补充时的打断），行为和现在一样。

**Key interfaces:**
- 通话里 `Speech` 端口的 `tts(api_key, voice_id, sample_rate) -> TTSService`：Soniox/Fish 的实现现在直接返回 `FishAudioTTSService`，可以改为返回一个调整了打断处理顺序的子类或包装；或者在 TTS 之后放一个处理器。二选一，由实现者定。
- Pipecat 里相关的是 `TTSService.process_frame` 对 `InterruptionFrame` 的处理，以及 `InterruptibleTTSService._handle_interruption`。只在本仓库里覆盖或包装，不改 Pipecat 本身。

**Acceptance criteria:**
- [x] 测试（语音通话层面，假 TTS 的 `_connect` 或断开故意很慢）：角色说话时被打断，下游在重连完成之前就收到 `InterruptionFrame`。
- [x] 测试：重连完成前送来的新回复文字，在重连后被合成，没有丢失。
- [x] 测试：角色没在说话时的打断，不触发重连，行为不变。
- [x] 真实通话验证：按 02 的场景（角色说完第一段、后面还在生成时插话）再做一次，从 `InterruptionFrame` 到客户端静音在几百毫秒以内，`done` 不再晚到约 1 秒。在 Comments 里记下时间线。
- [x] `uv run pytest`、`uv run pyright`、`npm test`、`npm run typecheck` 全部通过（`test_characters.py` 里那个 Windows 路径分隔符的已知失败除外）。

**Out of scope:**
- 缩短 Soniox 判定用户开始说话的时间（约 0.8–1.2 秒）。
- 改 Pipecat 本身，或者换 TTS 服务。
- 补充和打断的判定规则（01、02 已定）。
- 静音通话：没有声音，本来就不受影响。

### 实现（2026-09-27）

- **`InterruptsFirst`**（`call.py`）：混在 `InterruptibleTTSService` 的具体服务前面，`FishTTS(InterruptsFirst, FishAudioTTSService)`（不叫 FishVoice：「音色」在 `CONTEXT.md` 里指声线模型），由 `SonioxFishSpeech.tts` 返回。
  - `_handle_interruption` 做 `InterruptibleTTSService` 做的事（判断要不要重连、清 `_tts_started`、调 `TTSService` 的收尾），但不在原地重连，而是开一个后台任务 `_reconnect`（先等上一次还没做完的重连，再断开、连上）。打断随即由 `process_frame` 往下游推。
  - `run_tts` 和 `flush_audio` 先等重连做完，所以重连期间送来的文字不丢，也不会发到正在关的连接上。
  - 等重连用 `asyncio.wait`，而不是直接 `await` 任务。Pipecat 每次打断都会取消 process 任务，直接 `await` 会连被等的重连任务一起取消，之后的重连和合成都会在 `CancelledError` 上卡住，角色从此不再出声（code review 发现）。重连失败时，服务保持断开，下次合成时 Fish 自己会连上。
  - `stop`、`cancel` 先取消还在进行的重连，挂断后不会再连上。
- **比工单多发现的一点**：`RTVIServerMessageFrame` 和 `InterruptionFrame` 一样是 `SystemFrame`，走同一个输入任务。所以只把原地重连挪到推打断之后还不够，`done` 仍然要等重连；重连必须放到后台。
- 打断之后、重连完成之前，旧连接上 Fish 还会发来一些音频。这时打断已经把当前的音频上下文清掉了，这些音频找不到上下文，会被丢掉（Pipecat 原有的行为），所以不会漏出来。
- **测试** `test_voice_interruption.py`：替身 `SlowSocketTTS` 连接、断开各要 0.3 秒，像 Fish 一样在 setup 时连接。工单原来说放在 `test_voice_call.py`，但那里测的是信令，没有帧层面的切入点，所以另开了一个文件。
  - 角色说话时被打断：打断和其后的 `done` 在断开、重连之前到达输出端；
  - 打断后的新回复在重连完成后合成；
  - 角色没在说话时的打断不重连；
  - 重连途中挂断，之后不会再连上（去掉 `_stop_reconnecting` 时这条会失败）；
  - 等重连时又被打断，之后的回复照常合成（直接 `await` 时这条会卡住）；
  - `SonioxFishSpeech.tts` 返回 `FishTTS`。
- `uv run pytest`：519 通过，1 个失败是已知的 Windows 路径分隔符问题（`test_characters.py`）。`uv run pyright` 0 错误。`npm test` 60 通过，`npm run typecheck` 通过。
