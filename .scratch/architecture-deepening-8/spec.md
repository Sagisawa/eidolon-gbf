# 架构加深（第八轮）：自带密钥只有一种形状，豁免规则只有一份

Status: ready-for-agent

术语以 `GLOSSARY.md` 为准；本轮在「运行记录」里写明了「用了自带密钥」对回合和对通话各指什么。设计词汇（module、interface、seam、adapter、depth、leverage、locality）取自 `codebase-design` skill。这是 2026-10-11 架构审查里的候选 2，经 grilling 定下设计；审查里的候选 4「前端发请求只有一条路」拷问后不单独做，剩下的整理并入本轮（见下）。前后端都改。

## Problem Statement

自带密钥只存浏览器（ADR-0017）上线以后，「这次带了哪些 key」「算不算限额」这两件事散在前后端好几处，已经各写各的：

- **「全用自带密钥才不计入」写了两份。** 后端按带来的服务算豁免；前端设置页另有一份同样的规则，用来告诉用户「全都不计入 / 只有文字对话不计入 / 都计入」。改一边忘一边，设置页就会对用户说错话。
- **「带来的 key」在线上有两种形状。** 文字回合在请求体顶层带 `own_llm`，通话的 offer 带 `own_keys.{llm,tts,stt}`；后端为此有两处把请求变成 `BroughtKeys`。
- **接通后不再带 key，靠的是第三方库的实现细节，没有测试。** 通话接通后，浏览器从之后每次重新协商要发的请求数据里删掉 key；这只因为 Pipecat 按引用持有那份请求数据才有效。哪天它改成拷贝一份，key 就会随每次重新协商重发，没人会发现。整个通话的前端连接没有测试。
- **同一份列表在前端抄了几份。** 语音识别服务商写了三份（请求类型、本地存储的取值表、设置页的选项），LLM 协议两份；请求函数的文件和本地存储的文件互相引用类型。
- **运行记录里「用了自带密钥」有两种意思。** 通话记的是「三项全自带」，通话里的回合记的是「自带了 LLM」，后台都标「自带密钥」，字段名看不出区别。
- **「key 不出服务器」缺一条验证。** 通话中途自带的语音 key 失败时，日志和发给用户的原因里会不会带出 key，没有测试。
- **（并入的候选 4）请求的写法不统一。** 带时区头、遇到未登录或未同意就跳转的那个请求函数是私有的；后台四个 lib 只好各自手写请求或另写一份；登录选项、同意、开发登录、登出四个请求也绕开它，原因没写。RTVI 的说话事件（`SPEAKING`）不是服务器的消息，却放在请求函数的文件里。

## Solution

- 前端的自带密钥 module 收齐：类型、协议和服务商列表只有一份；一次回合或通话要带什么，由它拼成同一种形状；设置页的豁免说明改问服务器。
- 文字回合和通话都带 `own_keys`，后端只有一处解析。旧页面还发 `own_llm` 时，后端拒绝并提示刷新，不会悄悄改用部署者的 key。
- 服务器新增一个只问不取的豁免接口，豁免规则只剩后端一份。
- 「接通后不再带 key」和「通话中自带语音 key 失败不泄漏」各有测试守着。
- 运行记录里那个字段按 GLOSSARY 的定义改名。
- 前端所有对后端的请求都走同一个请求函数。

## User Stories

1. 作为用户，我想设置页告诉我哪些用量不计入限额，说法和服务器实际怎么算永远一致。
2. 作为用户，我想只填了 LLM 的 key 时，设置页说「文字对话不计入」；三项都填了时说「都不计入」；没填 LLM 时说「都计入」，和现在一样。
3. 作为用户，我想设置页还没问到或者问失败时，这句说明先不显示，而不是显示一句可能不对的话。
4. 作为用户，我想文字回合照旧用我在这个浏览器里存的 LLM，每次发都现读，别的标签页改了下一次就用上。
5. 作为用户，我想文字回合只带我的 LLM key，即使我存了语音 key 也不随文字回合发出去。
6. 作为用户，我想通话照旧带上我存的三项 key，用谁的服务、算不算限额都和现在一样。
7. 作为用户，我想接通以后，之后每次重新协商都不再把我的 key 发出去。
8. 作为部署那一刻还开着旧页面的用户，我想发文字回合时被告知「页面已经更新，请刷新后再发」，而不是回合悄悄改用部署者的 key、还计入我的限额。
9. 作为用户，我想通话中我自带的语音合成或语音识别 key 失败时，看到的原因里没有我的 key。
10. 作为部署者，我想服务器的日志里永远不出现用户的 key，包括通话中自带语音 key 失败的时候。
11. 作为用户，我想在同意页点「同意」时会话恰好已经过期，会被送回落地页登录，和其他页面一样。
12. 作为管理者，我想看板和用户详情里的「自带密钥」统计口径不变：回合指用自带 LLM 的，通话指三项全自带、不计入限额的。
13. 作为管理者，我想后台的各个页面照旧工作，行为不变。
14. 作为开发者，我想「全用自带密钥才不计入」只在后端写一份，前端不再有拷贝。
15. 作为开发者，我想「带来的 key」在文字回合和通话里是同一种形状，后端只有一处解析。
16. 作为开发者，我想语音识别服务商、LLM 协议这些取值在前端只写一份，加一种时编译器会告诉我还漏了哪里。
17. 作为开发者，我想请求函数的文件和自带密钥 module 之间不再互相引用。
18. 作为开发者，我想不跑真的 WebRTC，就能测到通话的 offer 带了 key、之后的重新协商不带。
19. 作为开发者，我想所有对后端的请求都经同一个请求函数，带同样的头、按同样的规则跳转和报错。
20. 作为开发者，我想运行记录里那个字段的名字说清楚它对回合和对通话各记的是什么。
21. 作为开发者，我想后端不再有只做转发的「通话预检豁免」那一层。

## Implementation Decisions

### 线上：带来的 key 只有一种形状

- 文字回合的请求体改为 `{ text, own_keys?: { llm? } }`，通话的 offer 照旧在请求数据里带 `own_keys: { llm?, tts?, stt? }`。两者的 `own_keys` 是同一种结构（后端的 `OwnKeysInput`），每项都可以没有。
- 浏览器只带这次用得上的：文字回合只带 LLM；通话带存了的全部三项。
- 后端的文字回合和通话都经 `OwnKeysInput.brought()` 得到 `BroughtKeys`，删掉文字回合里另外拼 `BroughtKeys` 的那一处。文字回合即使收到语音 key 也不用（豁免只看 LLM，本来就是这样）。
- 文字回合的请求体里如果还有旧字段 `own_llm`，回 422，原因是「页面已经更新，请刷新后再发」。这是一段过渡代码，注明以后可以删。
- 拨号前的预检照旧只报服务名、不带 key（`/api/ice-servers?own=llm,tts,stt`），ADR-0017 有意这样做，不变。

### 后端：豁免规则一份，新增只问不取的豁免接口

- `OwnKeys` 的豁免规则改为按用量种类回答：给定用量种类（回合或通话）和带来的服务，答这种用量算不算豁免。不再返回按字符串取值的 dict。`for_turn`、`for_call`、通话预检都用它。
- 新增 `GET /api/account/keys/exemption?own=…`（服务名逗号分隔，可以为空），返回 `{ turns: bool, calls: bool }`。只按规则算：不碰部署者的 key，也不看这位用户的个人限额；通话不可用时照样回答。要求已登录并同意条款，和其他 `/api/account` 接口一样；不认识的服务名回 422，和预检一致。
- 删掉 `Admissions.call_setup`（只是转发）。通话预检直接问 `OwnKeys`：先确认语音识别和合成都有 key（没有就是通话不可用），再按通话的规则答豁免。

### 运行记录：字段名说清意思

- 意思不变（GLOSSARY「运行记录」已写明）：回合（包括通话里的回合）记的是扮演角色的 LLM 是否用户自带；通话记的是三项是否全都自带，也就是是否不计入限额。
- 代码里的字段改成能说清这层意思的名字，并在定义处写明对回合和对通话各指什么。数据库的列名、看板和用户详情的 JSON 字段名、前端的文案都不改。

### 前端：自带密钥 module

- 在现有的本地存储自带密钥的 module 基础上收齐，对外提供：
  - 类型：服务名、LLM 协议、语音识别服务商、百炼地域、各项 key 的结构。LLM 协议和语音识别服务商各有一份取值列表，设置页的选项从这里来。以上都从请求函数的文件里搬过来，请求函数的文件改为从这里引用类型。
  - 存、删、读（按用户分开，存储不可用时不抛错，和现在一样）、能不能存的探测、只露末 4 位。
  - 一次文字回合要带的 `own_keys`（只有 LLM，没存就不带），和一次通话要带的 `own_keys` 加上服务名列表（预检用）。都在调用时现读。
- 删掉前端的 `limitExemption`（以及它的文件和测试）。设置页存的 key 有变化时，按存了哪些服务问豁免接口，用返回的 `{turns, calls}` 选三句说明之一（文案不变）；还没问到或者问失败时不显示这句。
- `sendTurn` 和 `startCall` 照旧收 userId、每次现读；只是读出来的东西改由自带密钥 module 拼好。
- `startCall` 照旧在接通后从请求数据里删掉 key，写明为什么，并由测试守着（见下）。

### 前端：请求都走同一个请求函数（并入的候选 4）

- 导出请求函数（加时区头；遇到未登录跳落地页、未同意跳同意页）。后台的用户、配置、单价、看板四个 lib 都改用它，删掉用户 lib 里另写的那一份。后台接口对没登录或不是管理者的人一律回 404（`admin_api` 写明的设计），所以行为不变。
- 登录选项、同意、开发登录、登出四个请求也改走它。逐个核对过后端：登录选项公开，登出总是 204，开发登录不会回 401，所以都不变；唯一的变化是同意请求在会话过期时回 401，现在会跳回落地页登录，而不是显示「请先登录」。
- 新增豁免查询的请求函数，也走它。
- RTVI 的说话事件（`SPEAKING` 和 `Speaking`）从请求函数的文件搬到通话连接的 module；它们是 Pipecat 的标准事件，不是服务器的消息。角色、消息、记忆、通话事件这些服务器响应的类型留在请求函数的文件里。

## Testing Decisions

- **好的测试**经由 module 的 interface 断言看得见的结果：请求带了什么、服务器回什么、用的是谁的服务、计不计入限额、日志和给用户的原因里有没有 key。不检查内部状态。先写会失败的测试（`/tdd`），再改实现。
- **后端，走 HTTP**（`make_client`，`FakeLLMService`、`FakeSpeech`；仿 `test_own_llm.py`、`test_own_speech_keys.py`、`test_rate_limit.py`）：
  - 文字回合带 `own_keys: {llm}` 时跑在自带的 LLM 上、不计入限额；不带时跑在部署者的上、计入。测试辅助函数 `send_turn` 改为发新形状。
  - 带旧字段 `own_llm` 的文字回合回 422，原因是要刷新；没有跑任何 LLM，没有计入限额。
  - 豁免接口：没有服务、只有 LLM、LLM 加一项语音、三项全有，各答什么；部署者没配语音时照样回答；不认识的服务名回 422；未登录 401、未同意 428。
  - 通话预检的行为不变（已有测试照旧通过）。
- **后端，豁免规则本身**：`test_own_keys.py` 里已有的表驱动用例改成按用量种类问，继续直接测 `OwnKeys`。
- **后端，key 不出服务器**（仿 `test_own_keys_in_logs.py`，经 `Browser.call` 跑真实的 WebRTC）：通话中自带的语音合成 key、自带的语音识别 key 各失败一次，抓 logging 和 loguru 的输出，断言找不到 key；通话结束消息里给用户的原因也没有 key。如果测出泄漏，在同一张票里把漏的那一处遮掉。
- **前端，自带密钥 module**（仿 `localOwnKeys.test.ts`，`vi.stubGlobal` 换掉 localStorage）：文字回合只带 LLM、没存 LLM 时不带；通话带存了的全部、服务名列表和存了的一致；存坏了的那一项当作没有（已有）。
- **前端，请求函数**（仿 `api.test.ts`，假的 `fetch`）：`sendTurn` 的请求体是 `own_keys` 的新形状；豁免查询发对的服务名、交回 `{turns, calls}`；同意请求遇到 401 时跳落地页。删掉 `ownKeys.test.ts`。
- **前端，新 seam：`startCall`**：用 `vi.mock` 换掉 Pipecat 的 client 和 WebRTC transport、以及麦克风，不跑真的 WebRTC。断言 offer 的请求数据带了 `own_keys`，接通后同一份请求数据里不再有它（也就是之后重新协商发出去的不带）。只测这一件事，不在这里测通话的其他行为（那些由 `liveConversation.test.ts` 经假的通话覆盖）。
- 后端 `pytest` 全部通过，`ruff`、`pyright` 没有新的报错；前端 `vitest`、`tsc`、`sh scripts/check-discipline.sh` 通过。

## Out of Scope

- `droppedEnd`（掉线的通话「除非全用自带密钥，否则计入」）不动：连接断了服务器没法再告诉浏览器，只能由浏览器推断，用的豁免值也来自服务器。
- 前后端之间的枚举不做代码生成；后端那份照旧，前端那份注明跟后端同步。
- 遮掉 key 的做法不重组，只补测试、修测出来的漏处。
- 豁免接口不看个人限额（不限、只能用自带密钥），设置页不新增这类说明。
- 后台会话过期时显示「Not Found」，不处理（会话按使用续期，很少碰到）。
- 运行记录的数据库列、看板和用户详情的统计口径与文案。
- 本机存储（隐藏 / 置顶、通话偏好、衣装等）的统一和登出清除：审查里的候选 3，这一轮不做。
- 通话界面的状态转换：审查里的候选 1，下一轮（`architecture-deepening-9`）做。

## Further Notes

- 分支 `architecture-deepening-8`，从 main 的 88db17b 开出；GLOSSARY「运行记录」的改动在这个分支上。
- 候选 4 不单独做的原因：审查报告说后台请求「漏了登录跳转」，是错的。后台接口对没登录的人一律回 404，跳转本来就不会发生；剩下的只是写法不统一。以后的架构审查不要再提「后台请求缺登录跳转」。
- 和 ADR-0017 一致：key 只存在浏览器里、随请求发送；这一轮只改 key 在前端怎么组织、在线上是什么形状。
- 六张票分三波，每次会话只做一波：
  - 第一波：01（前端的请求都走同一个请求函数）、02（通话中自带的语音 key 失败时不出服务器）、03（运行记录字段改名），互不依赖；
  - 第二波：04（文字回合也带 `own_keys`）、05（`startCall` 守住接通后不再带 key），都只依赖 01；
  - 第三波：06（豁免只问服务器），依赖 04。
