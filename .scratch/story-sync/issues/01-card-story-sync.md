# 01: 卡牌剧情同步（曳光弹）

**What to build:** 管理员运行 `eidolon story sync` 后，先导入 SCTranslationData 的汉化版，再从 ShinyColorsDB 镜像把剧情库里还缺的 P 卡、S 卡剧情作为原文剧情导入，带上真正的卡名和剧情标题。原文剧情遵循与现有导入相同的正式经历规则；已有汉化版的剧情不会被覆盖，之后到位的汉化版会取代原文剧情，而且仍在同一张卡下。没有变化的卡不重新下载，也不重新向量化。镜像连不上时，汉化版照常导入。

**Blocked by:** None (can start immediately)

**Status:** resolved

- [x] 新增 `eidolon story sync`，一次完成「导入汉化版 → 拉取并导入原文剧情」，结束时打印新增原文剧情数、保留的汉化版数、跳过的失败结局数和新向量化段数
- [x] 通过镜像 API 列出全部卡牌，读取每张卡的剧本编号、卡名和剧情标题，从镜像下载剧本 JSON 到本地缓存
- [x] 原文剧情的出处是卡名（与 SCTranslationData 的目录名同格式），标题是 API 给出的剧情标题
- [x] 剧情库已有汉化版的剧情不被覆盖；之后导入的汉化版取代原文剧情，剧情目录中仍在同一张卡下

## Comments

实现摘要：

- 命令：`eidolon story sync [--story 目录] [--cache 目录] [--idol N ...] [--characters 文件]`。汉化版目录默认取 `EIDOLON_STORY_PATH`（本地 `../corpus/SCTranslationData/data/story`，容器 `/corpus/SCTranslationData/data/story`），缓存目录默认取 `EIDOLON_MIRROR_CACHE_PATH`（本地 `../corpus/mirror`，容器是数据卷里的 `/data/mirror`，因为 `/corpus` 只读挂载）。退出码：0 完全成功；1 配置错误或向量化中断；2 镜像或 API 出错（汉化版已照常导入）。
- 下载层 `eidolon/mirror.py`：`idolList` → 每位偶像 `idolInfo` 的 `cardLists`（带 `cardHash`、`lastModified`，共约 33 次请求就能列出全部卡牌和它们有没有变化），变化了的卡才请求 `pCardInfo` / `sCardInfo`。没有用 spec 里的 `sitelist`：它只有日期，判断不了卡牌数据的变化，也不带卡牌类型。请求逐个发出、间隔 1 秒，带自己的 User-Agent；404 表示镜像没有这个剧本，不是错误；304 表示没变；其他状态码和连接错误都是 `MirrorError`。
- 同步 `eidolon/story_sync.py`：缓存目录里 `cards.json` 记着每张卡的版本、剧情列表和「是否全部拿到」，剧本按游戏路径存放（`scripts/produce_events/200100401.json`），旁边是 `.etag`。已有汉化版的剧情不下载；没变化且完整的卡不再请求；变化了的卡重新读详情，已缓存的剧本用条件请求；有剧本 404 的卡下次再试缺的那几个。剧本先写 `.part` 再改名，中断不会留下半个文件。镜像中途出错时，已经下载的剧本照样导入。
- 导入：`story_import` 新增 `import_script_files`，由调用方提供出处（卡名）和标题，其余规则与 JSON 导入完全共用。另外两处通用改动：剧情库里已有一模一样的剧情时不再重复保存（报告 `unchanged`），这样每周同步重新读取整个缓存也不会重写数据库；JSON 台词里游戏的 `\r\n` 换行统一成 `\n`，与 SCTranslationData 一致（否则汉化版取代原文剧情前后的日语文本会不同）。
- 输出：汉化版的导入数、未变化数、失败结局数；原文剧情的下载数、新增或更新数、保留的汉化版数、镜像上还没有的剧本数；合计的失败结局数和新向量化段数。
- 测试：`test_story_sync.py`（切入点 B），`FakeShinyColorsDB` 用 `httpx.MockTransport` 扮演 API 和镜像（ETag、304、404、连不上、第 N 次请求后断开），`FakeEmbedder` 断言不重新向量化；覆盖卡名和标题、正式经历规则、剧情目录、汉化版不被下载和覆盖、之后的汉化版取代原文剧情且仍在同一张卡下、失败结局、第二次同步零下载零向量化、未变化的卡不再请求、变化的卡只重新下载变了的剧本、404、镜像连不上、镜像中断后续传、向量化中断后续传、`--idol`、请求间隔、命令行退出码 2 和缺少目录。

真实镜像验证（2026-09-26，假向量化，只同步櫻木真乃的 4 张 P_SSR / S_SSR 和 1 张 P_R）：

- 空剧情库：两张 P_SSR 共 10 个剧本全部下载并导入，出处是 `【ほわっとスマイル】櫻木真乃` 这样的卡名，标题是游戏里的剧情标题（「ほわほわアイドル」「真乃ならできる」……），分类 P卡剧情；S_SSR `【トリプルイルミネーション】櫻木真乃` 的 4 段是 S卡剧情，灯織出场的几段被识别为 hiori 出场。P_R 没有剧情，不请求剧本。请求间隔实测约 1.2 秒。第二次同步只发出 1 次请求（`idolInfo`），0 下载、0 向量化。
- 放入真实 SCTranslationData 里真乃这三张卡的 12 个 CSV 后用新缓存重跑：这 12 段保留汉化版，镜像上一个都没有下载；只有 SCTranslationData 没有的 `【ハ♡トフェルトゥギフト】` 5 段作为原文剧情导入。汉化版 CSV 的目录名、文件名与 API 的卡名、剧情标题完全一致，CSV 的日语台词与镜像 JSON（换行统一后）逐字相同。
- 真实剧本 JSON 就是帧数组，与 MVP 09 依据的格式一致：台词在 `text`，`id` 是数字，换行是 `\r\n`，选项帧只有 `select` 和 `nextLabel`（选项文字里也有 `\r\n`），导入没有警告。MVP 09 留下的「没有用真实 JSON 验证过」可以关闭。

留给后续的注意点：

- 选项分支之后，真实剧本里制作人会把选项原话再说一遍（`{"label": "1"}` 后面的 プロデューサー 台词），这几句作为普通台词保留了，所以每个选项的原话都会出现在剧情里（CSV 版本同样如此）。这不违反「不认定制作人选了哪一项」，但剧情里制作人会连说几句不同的话。
- `cards.json` 只在一张卡处理完后保存；中途中断的那张卡下次会重新读详情，已下载的剧本走条件请求（304），不重新下载。
- 生产 compose 的挂载、定时脚本和 cron 说明留给 04。

代码审查（/code-review）后的修改：

- 统计改为本次同步的数字：汉化版和原文剧情都分开报告新增和更新；汉化版一行另报告「取代了原文剧情」的段数（`ImportReport.untranslated_replaced`）；「已有汉化版」只统计本次检查过的卡牌，没有变化的卡不再计入，所以每周日志不会重复同一个大数。
- API 返回的数据结构和预期不同（缺字段、类型不对）也算镜像错误：报告错误、退出码 2，已下载的剧本照常导入，不再以 traceback 崩溃。

- 补充测试：成功时退出码为 0、报告内容；API 数据结构变化。
