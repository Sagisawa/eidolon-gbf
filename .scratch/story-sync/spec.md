# 剧情库与原作同步

Status: ready-for-agent

术语以 `CONTEXT.md` 为准（尤其是新增的「原文剧情」）；相关决策见 ADR-0003（剧情库与音色仅限私用）、ADR-0004（原文剧情从 ShinyColorsDB 镜像拉取）。

## Problem Statement

剧情库目前只来自粉丝维护的 SCTranslationData。它靠译者逐段手动导出再翻译，所以：

- 新剧情要等几周到几个月才进入剧情库，有的永远不会被收录；
- 很多旧剧情从来没人翻译，角色就回忆不起来；
- 更新全靠我手动重新克隆再导入。

结果是游戏里刚出的卡和活动，角色完全不知道；我想聊新剧情时，她们一脸茫然。

## Solution

新增一个同步命令，由服务器每周自动运行一次，每次做两件事：

1. 拉取最新的 SCTranslationData，导入汉化版；
2. 从 ShinyColorsDB 的解码镜像拉取剧情库里还缺的剧情的日语原文，作为原文剧情导入。

原文剧情和日后的汉化版是同一段剧情（同一个剧本编号）：汉化版到位后取代原文剧情，不会多出一段。角色回忆原文剧情与其他剧情没有区别。

三类剧情分别这样找到：

- **卡牌剧情（P 卡、S 卡）**：镜像 API 能列出全部卡牌，每张卡有剧本编号、日语标题和卡名。首次全量补齐，之后只拉新卡和有变化的卡。
- **培育剧情**：来自各偶像游戏内相册的数据（2024 年 3 月之后没再更新），带标题。首次补齐一次即可。
- **活动剧情**：API 里没有目录，按剧本编号的规律推算（`4001` + 三位活动编号 + 两位话数）。补齐粉丝版缺的活动，之后每次试探最新活动之后的几个编号。活动名由我手动维护的对照表提供，没填时用「活动剧情 NNN」和「第N話」占位。

## User Stories

### 时效

1. 作为用户，我希望游戏里新出的卡和活动剧情在一周内就能被角色回忆起来，以便和她们聊最近的剧情。
2. 作为用户，我希望角色回忆原文剧情时和回忆汉化过的剧情一样自然，不会提到「还没翻译」之类破坏沉浸感的话。
3. 作为用户，我希望问角色「最近那次活动讲了什么」时，她能说出活动的正式名称（只要管理员填了对照表）。
4. 作为用户，对照表还没填的活动，我希望角色仍然能回忆内容，只是说不出活动名，而不是说出一个编造的名字。

### 覆盖范围

5. 作为用户，我希望 SCTranslationData 没翻译过的旧卡牌剧情也能被角色回忆起来。
6. 作为用户，我希望 SCTranslationData 缺失的旧活动剧情也能被补齐。
7. 作为用户，我希望相册里有、但 SCTranslationData 没收录的培育剧情也能被补齐。
8. 作为用户，我希望补齐的剧情同样只包含正式经历：失败结局不进入剧情库，选项分支只保留角色的反应。

### 汉化版取代原文剧情

9. 作为用户，我希望一段剧情的汉化版到位后，剧情库里只有带中文翻译的那一份，而不是原文和汉化各一份。
10. 作为用户，我希望同步永远不会用原文剧情覆盖已经有汉化版的剧情。
11. 作为用户，我希望原文剧情被汉化版取代后，剧情目录里它仍然在原来那张卡或那个活动下面，不会分裂成两组。

### 剧情目录

12. 作为用户，我希望原文剧情在剧情目录里显示真正的卡名和标题（来自镜像 API 或相册），而不是一串剧本编号。
13. 作为用户，我希望活动剧情按活动归组，话数按顺序排列。

### 管理员：运行与部署

14. 作为管理员，我想用一条命令完成同步，以便不再手动重新克隆和分两步导入。
15. 作为管理员，我想让服务器每周自动运行一次同步，以便我什么都不做剧情库也会保持更新。
16. 作为管理员，我想在日志里看到每次同步新增了多少原文剧情、多少被汉化版取代、跳过了多少失败结局、新向量化了多少段文本。
17. 作为管理员，我希望镜像暂时不可用时，同步只是这一次拉不到原文剧情，已经导入的剧情和汉化版的同步都不受影响，下次运行会自动补上。
18. 作为管理员，我希望同步中途失败后重新运行能接着做，而不是从头下载和向量化。
19. 作为管理员，我希望没有变化的剧情不会被重新下载，也不会被重新向量化，以便每周的同步又快又省。
20. 作为管理员，我希望同步对镜像保持礼貌（逐个请求、大约每秒一个），以免给志愿者的服务器添麻烦。
21. 作为管理员，我想维护一份「活动编号 → 正式活动名」的对照表，每月加一行即可。
22. 作为管理员，修改对照表后，我希望下一次同步就能把活动名更新到剧情目录里。
23. 作为管理员，我希望首次补齐培育剧情后，命令列出标题里带「敗」「失敗」但没有被失败结局规则排除的剧情，以便我人工核对是否漏掉了失败结局。
24. 作为管理员，我希望拉取的原始剧本只存在服务器本地、不进入仓库，以符合剧情库仅限私用的约定。

## Implementation Decisions

- **一条同步命令，git 留在外面**：新增 `eidolon story sync` 子命令，参数包括 SCTranslationData 的剧情目录、原始剧本缓存目录、活动名对照表路径（都有合理默认值）。更新 SCTranslationData 的 `git pull` 由部署侧的定时脚本完成，应用里不调用 git。
- **导入顺序**：同步先导入汉化版（沿用现有 CSV 导入），再导入原文剧情（沿用现有 JSON 导入的规则：已有 CSV 版本时保留 CSV 版本）。失败结局、选项分支、出场角色、分类、分块向量化、同一剧本多份文件的取舍，全部复用现有导入流程，不另写一套。
- **原文剧情的出处和标题**：卡牌剧情取 API 的卡名（格式与 SCTranslationData 的目录名一致，都是「【卡名】角色名」）和剧情标题；培育剧情取相册的标题；活动剧情取对照表的活动名，没有就用「活动剧情 NNN」，标题用「第N話」。现有 JSON 导入只能从路径推断出处和标题，需要扩展为可以由调用方提供。
- **下载层**：一个镜像客户端，基于项目已有的 httpx，负责：
  - 列出卡牌、读取卡牌详情和相册数据；
  - 下载剧本 JSON 到本地缓存，并记下每个文件的 ETag，下次用条件请求（304 即未变化，不下载）；
  - 404 视为「这个编号不存在」，不是错误；
  - 请求逐个发出，间隔大约一秒。
- **活动编号推算**：已知活动编号来自剧情库和缓存里已有的活动剧情。每次同步先补齐已知范围内缺失的活动编号，再从最大的已知编号往后试探几个（先试第 01 话），找到的活动再逐话拉取直到 404。
- **活动名对照表**：一个小配置文件，格式和现有的角色配置风格一致；它和角色配置一样属于部署配置，示例文件进入仓库，真实文件只在服务器上。
- **失败嫌疑清单**：同步结束时，列出本次导入的培育剧情中标题带「敗」「失敗」、但没有被失败结局规则排除的剧情。这沿用现有 CSV 导入对文件名的警告逻辑，改为也看标题。
- **中断与重跑**：下载按剧本落盘，已下载的不重复下载；导入沿用现有「按批保存，向量化失败后重跑即可继续」的行为。
- **镜像不可用**：API 或镜像连不上时，报告错误并跳过原文剧情这一步；汉化版的导入照常完成。命令的退出码能区分「完全成功」和「部分失败」，以便定时脚本写日志。
- **部署**：
  - 生产环境的 compose 为缓存目录和对照表增加挂载；
  - 新增一个定时脚本，执行 `git pull` SCTranslationData，然后通过 `docker compose exec` 运行同步，并把输出追加到日志；
  - `docs/deploy.md` 说明如何安装主机上的 cron，以及首次全量补齐大约要一到两小时。

## Testing Decisions

- **只测外部行为**：测试只调用同步入口，然后通过 `StoryCorpus` 的查询（`get`、`catalog`、台词有没有中文翻译）检查结果，不断言下载、缓存和编号推算的内部细节。这与 MVP 的切入点 B 一致。
- **假镜像**：用 `httpx.MockTransport` 同时扮演 ShinyColorsDB 的 API 和镜像，提供样例卡牌列表、卡牌详情、相册数据和剧本 JSON，并对不存在的编号返回 404、对未变化的文件返回 304。先例：`test_embedding.py`、`test_llm_protocols.py`、`test_llm_config.py` 里的 MockTransport 用法。
- **假向量化**：沿用 `tests/fakes.py` 的 `FakeEmbedder`，用来断言「第二次同步不重新向量化」。先例：`test_story_import.py` 的幂等测试。
- **样例数据**：沿用 `tests/stories.py` 的样例剧本和 SCTranslationData 目录布局，补充镜像侧的样例。
- **要覆盖的行为**：
  - 原文剧情入库，带卡名和标题；
  - 已有汉化版的剧情不被覆盖；
  - 之后的汉化版取代原文剧情，而且仍在同一张卡下；
  - 失败结局被排除；
  - 第二次同步零下载、零向量化；
  - 镜像连不上时汉化版照常导入；
  - 活动编号的补齐与试探，以及对照表和占位名；
  - 培育剧情的失败嫌疑清单。
- 另外，01 的验收包括一次对真实镜像的小规模同步（例如只同步一位偶像的几张卡），用来验证真实剧本 JSON 的格式。它不进入自动测试。

## Out of Scope

- 自己编写游戏资源下载器（ADR-0004 中镜像失效时的后备，现在不写）。
- 用浏览器插件逐段导出剧情。
- 用后台模型为原文剧情机翻中文，或为活动编造名称。
- 失败时的主动通知（邮件、推送等），只写日志。
- 上游删除的剧情从剧情库中移除（现有导入同样不做）。
- 2024 年 3 月之后新增的培育模式的剧情（相册数据不再更新，没有编号来源）。
- 主页剧情、营业剧情等 API 和相册都不提供编号的剧情类型。
- 《偶像大师 闪耀色彩 Song for Prism》（シャニソン），它是另一款游戏。

### 数据来源速查（2026-09-26 实测，实现时再核对）

**API（`https://api.shinycolors.moe`）**

- 路由定义在 GitHub 的 ShinyColorsDB/ShinyColorsDB-ApiServer 仓库，文件 `src/info/info.controller.ts`。
- `/info/sitelist2`：纯文本，一次返回全部卡牌 UUID。
- `/info/sitelist`：XML，同样列出全部卡牌，每张卡带 `lastmod`，可以用来判断哪些卡有变化。
- `/info/pCardInfo?cardId=<uuid>`：返回 `cardIdolEvents[]`，每项是 `{eventCategory, eventId, eventTitle}`。P_SSR 通常有 4 个アイドルイベント，另加 1 个アフターストーリー。
- `/info/sCardInfo?cardId=<uuid>`：返回 `cardSupportEvents[]`，每项是 `{eventId, eventName, …}`。
- 部分卡牌没有剧情，例如最新的一张 S_SSR、PCup 的 S_SR、IdolRoad 的 P_SR。
- 卡名、卡牌类型（`P_SSR` 等）和发布日期：卡牌详情里有，`/info/idolInfo?idolId=N` 返回的 `cardLists[]` 里也有。
- `/info/idolList`：全部偶像，编号 1–28、91（はづき）和 801–804（【推しの子】联动）。

**剧本镜像**

- 地址是 `https://viewer.shinycolors.moe/json/<type>/<id>.json`。S 卡剧情（3 开头的编号）也在 `produce_events/` 下。
- 内容是帧数组，与现有 JSON 导入的格式一致；台词换行是 `\r\n`，选项是 `{"select": …, "nextLabel": …}`。
- 不存在的编号返回 404（HTML 正文）；目录路径返回 403，所以没有文件列表。
- 支持 `ETag`、`Last-Modified` 和条件请求（304）。

**相册（培育剧情的编号来源）**

- 地址是 `https://cf-static.shinycolors.moe/albums/album/NN.json`，NN 为 01–28。
- `communications[]` 每项带 `communicationId`、`communicationCategory` 和 `title`。
- 最后更新于 2024-03。
- 分类到剧本类型的对应：
  - character / season / unit / concert_event → `produce_events`
  - communication_morning → `produce_communications`
  - cheer → `produce_communication_cheers`
  - audition → `produce_communication_auditions`
  - birthday / present / seasonal / special → `special_communications`
- 失败结局在相册里多有标注（「シーズンN（失敗）」「敗退コミュ」「…敗北」），但也有例外：`produce_events/600100107`「未来へ羽ばたく」其实是 W.I.N.G. 落败结局。它能被现有规则认出。

**活动剧情**

- 编号是 `4001` + 三位活动编号 + 两位话数，几乎每个活动 8 话。
- SCTranslationData 里的活动编号范围是 001–086，其中缺 002、003、005、006、008、010、016、024、056、061、062、064、065、066、070、071、072、077。
- 镜像实测：002、056、077、087–097 都存在，097 有第 08 话、没有第 09 话，098 返回 404。
- 另有两个特殊编号 490170000 和 490180000，不符合上面的规律。
