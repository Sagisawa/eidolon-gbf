# 04: 对话模型分「文字」「通话」两项强度

**What to build:** 部署者可以只调低通话的思考强度，文字对话保留原来那一档。通话里的回合用通话那一项，文字回合用文字那一项。两项不同时，保存时各检查一次。背景见 `../spec.md`「模型设置」「保存时的检查」。

**Blocked by:** 03（单项强度的整条链路在 03 里）

**Status:** ready-for-agent

**难度：中。** 难点在部署者那边拿模型的地方：现在通话和文字回合拿到的是同一个对话模型，要让通话拿到用通话强度派生出的那一份。表单和 `.env` 只是在 03 的基础上多一项。

## 已定的设计（详见 spec）

- 对话模型存两项强度：03 里的那一项就是「文字」，新加「通话」。`.env` 加 `CHAT_LLM_CALL_REASONING_EFFORT`。
- 由对话模型的设置派生出两份，只有强度不同，共用一个 HTTP 客户端。后台改了任一项，两份一起换。
- 提炼记忆用的是后台模型，不受这两项影响。
- 检查：两档相同只检查一次；不同各检查一次，报错前缀写明「文字的思考强度」或「通话的思考强度」。

## 验收

- [ ] 测试：文字回合发出的请求带文字档；通话里的回合带通话档（用现有的通话测试辅助，断言假模型或录制服务收到的请求）。
- [ ] 测试：通话那一项不设置时，通话的请求不带强度参数，即使文字那一项设了。
- [ ] 后台配置测试：两项分别保存、回退 `.env`；两档不同时检查跑两次，被拒那一档的报错前缀正确；两档相同只跑一次。
- [ ] 前端 `adminConfig` 纯函数测试：对话模型多出「通话」那一行，后台模型没有。
- [ ] 实测：线上的 DeepSeek 把通话设成「关闭」、文字不设置，保存成功；本地构建版上打一通电话确认能正常对话（假麦克风的做法见 `docs/agents/local-acceptance.md`）。
- [ ] `backend/` 下 `pytest`、`frontend/` 下 `npm test` 全部通过，`ruff`、`pyright`、`tsc` 没有新的报错。

## Comments

- 票 03 留下的：后台对话模型（`chat_llm`）已经有 `reasoning_effort`、`extra_body` 两个字段（`live_config.LLM_FIELDS` 两个模型共用），这一项就是「文字」；通话那一项只给对话模型加，别加进 `LLM_FIELDS`。前端 `adminConfig.ts` 里两个模型共用 `LLM` 这份 `ItemSpec`，对话模型要分出自己的一份。检查的前缀在 `llm/providers.check_chat_llm(llm, effort)` 里写死成「思考强度『…』被服务拒绝：」，这张票要让它带上「文字的」「通话的」。
- **待定（票 03 审查提出，留给用户决定）：** 记忆模型「跟随对话模型」时（`live_config._memory_follows`：`.env` 两个槽位相同、后台也没单独设），`_memory_values` 直接用对话模型生效的全部字段，`lease` 里提炼记忆还用的是对话模型的同一个客户端（`chat.again()`）。所以后台给对话模型设了强度或额外参数，提炼记忆也跟着用；而 `.env` 里只设 `CHAT_LLM_REASONING_EFFORT` 时两个槽位不同，记忆模型就不跟随、不带强度。这和本票「提炼记忆用的是后台模型，不受这两项影响」、规格「不在槽位之间回退」对不上（`max_tokens` 一直是这样）。要改的话，跟随时只沿用连接那几项（协议、地址、密钥、模型名），强度、额外参数、`max_tokens` 取后台模型自己的，记忆模型也就不能再共用对话模型的客户端。
