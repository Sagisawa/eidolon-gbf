# 备份的保留期、看板状态与恢复

Status: ready-for-agent

术语以 `GLOSSARY.md` 为准（「备份」的保留期改为部署者设定）；决策见 ADR-0012 及其 2026-10-15 修订。上一轮的备份功能见 `.scratch/db-backup/`。

## Problem Statement

- 保留期写死 30 天，部署者想少留几天也改不了；桶里的备份占多大空间只能自己去存储桶里看，也不会有任何提醒。
- 备份停没停、上一次成功是什么时候，只能登服务器 `grep logs/db-backup.log`；想立即备份一次也要 ssh 上去跑脚本。后台里完全看不到备份。
- 恢复要照 deploy.md 手动走五步，其中「停后端、换文件、删 `-wal`/`-shm`、启动」最容易出错，回滚时被替换的库直接就没了。
- 换服务器时不知道要带什么、怎么带：deploy.md 还说 `characters/` 被 git 忽略、要另外保存，其实它早已在仓库里；也没有一节讲搬家。

## Solution

1. **保留期和空间提醒**：`EIDOLON_BACKUP_KEEP_DAYS` 把保留期设成 1 到 30 天（默认 30，超过 30 按配置错误）；`EIDOLON_BACKUP_WARN_GB` 设了以后，桶里备份的总量超过它就在日志里提醒一句。每次备份顺带统计桶里备份的份数和总量。
2. **备份记录和「同一时间只有一次备份」**：cron、手动、后台按钮发起的每一次备份都在数据库里留一条记录；正在进行的那条同时充当锁，撞上的那次直接放弃。
3. **看板上的备份状态和「立即备份」**：看板在服务健康状态旁边显示备份：上一次成功的时间、结果、大小、桶里的份数和总量、保留期、上一次失败的原因；超过 26 小时没有成功、或者根本没配置备份，都标异常。「立即备份」在后台运行，进行中按钮显示「备份中…」。
4. **恢复命令**：`deploy/db-restore.sh <文件>` 接受在自己电脑上解密好的 `.db` 或 `.db.gz`，检查通过后先把要被替换的库备份一次，再停后端、替换、启动；新服务器上加 `--no-backup` 跳过备份。
5. **换服务器**：deploy.md 新增一节——在旧服务器上立即备份一次，新服务器照「部署」准备好 `.env`（原来的 `EIDOLON_SECRET_KEY`）和自己的 compose 叠加文件，再从那份备份恢复。不做本地备份，不做导出，后台不提供下载（ADR-0012 修订）。

## User Stories

1. 作为部署者，我想把备份的保留期设成比 30 天短，这样用户删掉的数据能更早从备份里消失、存储也更省。
2. 作为部署者，我把保留期设成超过 30 天或者不是整数时，想让备份以「配置不全」失败并说明原因，这样我不会无意中违背隐私政策里「最多 30 天」的承诺。
3. 作为部署者，我不设保留期时想沿用 30 天，这样升级以后什么都不用改。
4. 作为部署者，无论保留期设成几天，我都想让最新的一份备份永远保留，这样存储桶不会被删空。
5. 作为部署者，我想设一个空间阈值，桶里备份的总量超过它时日志里出现一条「注意」，这样存储费涨上去之前我能知道。
6. 作为部署者，空间超过阈值时我想让备份照常成功、退出码不变，这样提醒不会被当成故障、也不会让心跳停掉。
7. 作为部署者，我不设空间阈值时不想收到任何空间提醒，这样不会被某一家存储的免费额度误导。
8. 作为部署者，我想在每次备份的日志里看到桶里还剩几份备份、一共多大，这样不用登存储桶就能估算费用。
9. 作为部署者，我想让 cron 的备份和我在后台点的备份不会同时运行，这样两次备份不会互相抢磁盘和带宽、也不会在清理时互相干扰。
10. 作为部署者，撞上正在进行的备份时我想让这一次直接放弃，并在日志里写明「上一次备份还没结束」（退出码仍是 6），这样我知道这不是故障。
11. 作为部署者，备份进程中途被杀掉（容器重启、机器断电）以后，我想让下一次备份不被一把永远不放的锁挡住。
12. 作为管理者，我想在看板上看到上一次成功备份的时间、大小，桶里的份数和总量，以及现在的保留期，这样不登服务器就知道备份在正常工作。
13. 作为管理者，上一次成功的备份超过 26 小时时，我想让看板把备份标成异常，这样 cron 停了我能在看后台时发现。
14. 作为管理者，部署根本没有配置备份时，我想让看板显示「未配置」并标成异常，这样我不会以为数据是安全的。
15. 作为管理者，最近一次备份失败时，我想在看板上看到失败的原因（导出失败、上传失败、清理失败、配置不全），这样我知道该去查什么。
16. 作为管理者，我想看到每次备份是谁发起的（每天的 cron、服务器上手动运行、后台按钮），这样我能分清日志里的哪一次对应看板上的哪一次。
17. 作为管理者，我想在看板上点「立即备份」，这样更新前、搬家前不用 ssh 到服务器上跑脚本。
18. 作为管理者，点了「立即备份」后我想马上看到「备份中…」，按钮不能再点，几分钟后自动变成新的结果，这样我不用盯着页面也不会重复点。
19. 作为管理者，无论正在进行的备份是谁发起的（包括 cron），我都想看到「备份中…」，这样我不会误以为备份卡住了。
20. 作为管理者，「立即备份」失败时我想在看板上看到原因，和 cron 失败时看到的一样。
21. 作为管理者，空间超过部署者设的阈值时我想在看板上看到它被标出来。
22. 作为非管理者，我访问备份状态和立即备份的接口时只得到 404，和后台其他接口一样。
23. 作为部署者，恢复时我想把在自己电脑上解密好的 `.db` 或 `.db.gz` 交给一条命令，由它完成停后端、替换、删掉 `-wal`/`-shm`、启动，这样不会漏步骤。
24. 作为部署者，我交给恢复命令的文件损坏、不是 SQLite、或者不是本项目的数据库时，我想让它什么都不动就退出并说明原因，这样线上的库不会被一份坏文件换掉。
25. 作为部署者，在正在使用的服务器上回滚时，我想让恢复命令先把要被替换的库备份到存储桶，这样恢复错了还能回去，而服务器上不会多出一份没人管的旧库。
26. 作为部署者，替换前的那次备份失败时，我想让恢复命令停下、什么都不替换，除非我明确加了 `--no-backup`。
27. 作为部署者，在新服务器上（库是空的、备份可能还没配）恢复时，我想加 `--no-backup` 跳过先备份这一步。
28. 作为部署者，恢复完成后我想看到恢复进来的库里有多少位用户，这样我能马上判断是不是对的那一份。
29. 作为部署者，恢复以后我想让看板不会因为备份文件里残留的「进行中」记录而一直显示「备份中…」。
30. 作为部署者，换服务器时我想在 deploy.md 里找到一节完整的步骤：旧服务器上立即备份，新服务器准备 `.env` 和 compose 叠加文件，下载、解密、恢复、确认。
31. 作为部署者，我想在文档里知道新服务器部署的代码不能比旧服务器旧，这样不会把新表结构的库装进旧代码里。
32. 作为部署者，我想在文档里知道 `characters/` 在仓库里、不用另外保存，只有 `.env` 和服务器上自己加的 compose 文件要手动带走。
33. 作为部署者，我想在 `.env.example` 里看到保留期和空间阈值两个变量及其说明。
34. 作为用户，我在隐私政策和删除确认里看到的「备份中的副本最多 30 天后清除」在部署者调短保留期以后仍然成立。

## Implementation Decisions

### 保留期和空间（`eidolon.backup`）

- 备份设置从环境变量多读两项：保留天数（`EIDOLON_BACKUP_KEEP_DAYS`，整数 1–30，空着为 30，其他值是配置错误，`eidolon backup` 以退出码 1 结束）和空间阈值（`EIDOLON_BACKUP_WARN_GB`，正数，可以是小数，空着不提醒，其他值是配置错误）。只在 `.env` 里改，后台只显示（和其他备份设置一致）。
- 清理过期备份时按设置的保留天数判断，「永远保留最新的一份」不变；按对象名里的时间戳判断、名字不符的对象不动，都不变。
- 清理时列出桶里的对象要带上大小，备份结果（`BackupReport`）里多出桶里剩下的备份的总字节数；超过阈值时多出一条提醒，和心跳失败一样只是「注意」，不改变退出码、不影响心跳。

### 备份记录与锁

- 新增一张备份记录表：每次备份一行，记开始时间、结束时间（进行中为空）、来源（`cron` / `manual` / `admin`）、退出码、备份的对象名和大小、桶里剩下的份数和总字节数、是否超过阈值、错误原因（导出、上传、清理各一，配置不全也记）。不记任何用户内容。超过 90 天的记录在写新记录时顺带删掉（和运行记录的保留期一样）。
- 一次「备份运行」是 cron 的 `eidolon backup` 和后台按钮共用的唯一入口：先在表里插入一条进行中的记录作为锁——已经有一条开始不到 1 小时、还没结束的记录就放弃（线上一次备份约 3 分钟，1 小时足够判断进程已经死了）；然后执行现有的备份、清理、心跳；最后把结果写回这一条。锁放在数据库里而不是文件锁，因为本地开发在 Windows 上直接跑后端，`fcntl` 用不了，而 cron（`docker compose exec` 起的另一个进程）和后端进程共用同一个数据库文件。
- 配置不全也要留一条记录（没有进行中的阶段，直接写结果），这样看板能区分「没配置」和「配了但从没跑过」。
- `eidolon backup` 撞上锁时以退出码 6 结束，和 `deploy/db-backup.sh` 现有的「上一次备份还没结束」同一个码，脚本照原样把它传出去；脚本里主机上的 `flock` 可以保留，也可以去掉，由实现决定，但日志里的含义不变。
- 来源：`deploy/db-backup.sh` 区分 cron 和手动运行（例如手动时传一个参数、或 cron 那一行带一个环境变量），把来源交给 `eidolon backup`；后台按钮是 `admin`。
- 备份是用 `VACUUM INTO` 导出的，导出的那一刻这次备份的记录还在进行中，所以每份备份里都有一条「进行中」的记录。恢复时要把所有没结束的记录标成已放弃（见下文），否则恢复后看板会显示「备份中…」直到 1 小时的期限过去。

### 后台接口与看板

- 后台多两个接口，都只对管理者开放（`Admin` 依赖，非管理者 404）：
  - 读备份状态：是否配置了备份（不需要能连上存储桶，只看设置齐不齐；配置错误时附上原因）、保留天数、空间阈值、正在进行的那一次（开始时间、来源）、最近一次成功的那一次、最近一次的那一次（可能失败）、是否异常（未配置、配置错误、最近一次成功超过 26 小时或者从来没有成功过）。状态全部由后端算好，前端只显示。
  - 立即备份：已经有一次在进行就返回冲突，不再发起；否则在后端进程里起一个后台任务跑一次「备份运行」（来源 `admin`），立刻返回。配置不全时直接返回错误，不起任务。
- 后端进程里跑的备份要在线程里做导出、压缩、加密（这些是阻塞的），不能卡住事件循环和正在进行的通话；按钮那次的输出写进后端自己的日志。
- 看板在服务健康状态那一栏旁边加一块「备份」，前端轮询的频率和现有「进行中的通话」一样（每分钟），备份进行中时可以更快；按钮放在这一块里。文案进 `i18n/zh.ts`。照 `frontend/AGENTS.md` 的「shadcn 纪律」和 `DESIGN.md`。

### 恢复（`eidolon restore` + `deploy/db-restore.sh`）

- 新增命令 `eidolon restore <文件>`，在一个一次性的后端容器里运行（`docker compose run --rm --no-deps`，把文件只读挂进去），后端此时已经停了。它：接受 `.db` 或 `.db.gz`（按内容判断是否 gzip，不只看扩展名）；解压到数据卷里的临时文件；跑 `PRAGMA integrity_check`，确认有本项目的核心表（至少 `users`）；都通过才把临时文件改名替换现在的数据库（同一个卷里改名，替换要么成功要么不动），删掉旧的 `-wal`/`-shm`；把备份记录里所有没结束的记录标成已放弃；最后打印恢复进来的库里有多少位用户。任何一步失败都不碰现在的数据库，以非 0 退出并说明原因。
- `deploy/db-restore.sh <文件> [--no-backup]` 在主机上编排：检查文件存在；没加 `--no-backup` 时先运行 `deploy/db-backup.sh`（手动来源），不是 0 就停下、什么都不换，提示可以加 `--no-backup`；然后停后端、运行 `eidolon restore`、启动后端（`eidolon restore` 失败时也要把后端重新启动起来，库没被动过）。退出码和含义写在脚本开头，和 `db-backup.sh` 风格一致。
- 恢复之后表结构由后端启动时照常补齐；把新代码的库装进旧代码不做检查，写进文档。

### 文档

- `docs/deploy.md`：「备份」一节补上两个新变量和看板上的备份状态、「立即备份」；「从备份恢复」改成用 `deploy/db-restore.sh`（解密仍在自己的电脑上做）；新增「换服务器」一节；修正 `characters/` 被 git 忽略、要另外保存的过时说法（`characters/` 在仓库里；`deploy/event-names.toml` 只在写了的部署上才有，写了就一起带走）。
- `.env.example` 加上 `EIDOLON_BACKUP_KEEP_DAYS`、`EIDOLON_BACKUP_WARN_GB` 及说明（保留期只能 1–30 天，为什么）。
- 隐私政策和删除确认的「最多 30 天」不改：调短以后仍然成立。

## Testing Decisions

- 只测外部行为：一次备份运行之后桶里有什么、日志和报告里说了什么、退出码是多少、记录表里留下了什么；恢复之后数据库里是什么。不测内部函数怎么拆。
- **备份运行**（保留期、空间、锁、记录）：在现有的 `back_up` 之上加的「备份运行」入口测，照 `backend/tests/test_backup.py` 的写法——假的存储桶（`FakeBucket`）和 `httpx.MockTransport`，用固定的 `now`。覆盖：保留天数设成 7 时删掉 7 天前的、留下最新一份；超过 30、0、非整数是配置错误；阈值超过时有提醒但退出码 0、心跳照发；没设阈值时没有提醒；报告里的总量等于桶里备份对象的大小之和、不算名字不符的对象；进行中的记录挡住第二次运行（退出码 6）；开始超过 1 小时没结束的记录不挡；每次运行（包括配置不全）都留下一条记录；90 天前的记录被删掉。
- **`eidolon backup` 命令**：照 `tests/conftest.py` 的 `Admin` 驱动命令行，覆盖新变量配置错误时退出码 1、来源被记下来。
- **后台接口**：照 `backend/tests/test_activity_records.py` 用测试客户端打 `/api/admin/...`。覆盖：非管理者 404；未配置、配置错误、从没成功、26 小时以内、超过 26 小时这几种状态；进行中时立即备份返回冲突；立即备份起的任务跑完以后记录里来源是 `admin`。
- **恢复**：照 `Admin` 驱动 `eidolon restore`。覆盖：`.db` 和 `.db.gz` 都能恢复、数据和原库一致；损坏的文件、不是 SQLite 的文件、没有 `users` 表的 SQLite 都不碰现在的数据库；旧的 `-wal`/`-shm` 被删掉；没结束的备份记录被标成已放弃；用真实的一次备份（加密前的中间产物或测试私钥解开的文件）恢复以后能正常打开。
- **前端**：状态的文案和异常判断如果有前端逻辑，照 `frontend/src/lib/dashboard.ts` 旁边的单测；看板那一块在本地构建版上用 Playwright 验收（见 `docs/agents/local-acceptance.md`），状态由拦截接口造出未配置、异常、备份中、正常几种。
- **脚本**：`deploy/db-restore.sh` 和改过的 `deploy/db-backup.sh` 不写自动测试（和现有的部署脚本一样），在服务器上人工验收。

## Out of Scope

- 本地备份（备份写到服务器的目录里）、明文导出、后台下载备份（ADR-0012 修订）。
- 保留期超过 30 天、按份数或总量自动删除未过期的备份。
- 在后台修改备份设置（存储桶、公钥、保留期、阈值），在后台发起恢复。
- 在服务器上解密：私钥仍然只在部署者自己的电脑上。
- 带走 `.env`、compose 叠加文件、`corpus/`、原始剧本缓存、证书：前两个手动拷，其余可以重建。
- 恢复时检查表结构的新旧。

## Further Notes

- 线上一份备份压缩加密后约 77 MB、一次约 3 分钟（2026-10-15）；留满 30 天约 2.3 GB。
- 分两波：第一波 01（保留期、空间、记录和锁）；第二波 02（看板）和 03（恢复和换服务器）并行。03 本来不依赖 01，但「恢复时把没结束的记录标成已放弃」要用到 01 的记录表，排在 01 之后就不用回头补。
- `docs/deploy.md` 三张票各改各的段落：01 改「备份」里的变量和日志，02 在「备份」里加看板一段，03 改「从备份恢复」、新增「换服务器」、修正 `characters/` 的说法。
