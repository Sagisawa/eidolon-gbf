# 每回合变的内容放在历史后面，作为一条系统消息

服务商只缓存请求的开头，下一次请求开头一致的部分按缓存价收费（`deepseek-flash` 的命中价是未命中价的 1/50）。对话模型的请求里，每回合都会变的内容有：精确到分钟的当前时间、生日当天的提醒、好感度那几行、这回合找到的记忆、预先回忆的剧情和参考资料。这些内容如果放在开头的系统提示词里，后面的历史一个字都命不中，而历史正是随对话变长的那部分。所以请求按这个顺序排：

1. 共用固定部分：人设、世界设定、格式说明。同一位角色同一天对所有用户都一样。
2. 制作人资料：称呼、性别、生日日期。
3. 历史。
4. 一条系统消息，装每回合变的内容。
5. 这句话。对话事件的旁白照旧放在用户的话前面。

上一回合的请求去掉第 4、5 项，正好是这一回合请求的开头。

这条靠后的消息不带进之后回合的历史，所以不用存它。带的历史分段截断：后台设的回合数 N 是下限，攒到 N 加一半时一次砍回 N。这样历史的开头不会每回合挪一格。

依据是票 03 在 `deepseek-flash` 上的实测（`.scratch/prompt-caching/experiment.md`）：这种排法比原来的排法少花约 32% 的输入，去掉第一回合后，命中率从 69% 升到 83%。

## 各协议怎么发

- **Chat Completions**：开头连续的几条系统消息用空行拼成一条。靠后的这条原地发 `role: system`，DeepSeek 的编码器会把它渲染成独立的一段。
- **Responses**：开头连续的系统消息拼进 `instructions`。靠后的这条原地发一条 system 角色的输入项，不拼进 `instructions`，否则开头又会每回合都变。
- **Anthropic**：协议只有顶层的 `system`。对话中途的系统消息只有较新的 Claude 支持，第三方兼容服务大多不认。所以靠后的这条改成用户这一轮最前面的一个独立文本块。Claude 不按前缀自动缓存，要显式打断点，所以打两个：一个在共用固定部分末尾，一个在历史的最后一条消息上，让下一回合从这里接上。

第一个回合没有历史，这条消息紧跟在开头的系统消息后面，所以会和它们拼在一起（Anthropic 上会成为 `system` 的最后一块）。这对缓存没有影响。

## Considered Options

- **只追加**：每回合的动态内容留在之后发出的历史里。实测命中率比现在的做法高 8 个点，但几乎不省钱，因为分母变大了。提示词越来越长，第 10 回合已经是现在的 2.4 倍。另外还要多存一份「发给模型、不给用户看」的内容。
- **动态内容放进用户这句话里**：所有协议都能发。但这样角色会把系统给的信息当成制作人说的话，记忆和判断模型读到的这句话也会被污染。
- **保持原样，只把当前时间改粗**（例如精确到小时）：好感度、记忆、剧情照样每回合变，历史还是命不中。

## Consequences

- 保存时的检查也带一条对话中途的系统消息，和真实回合同样的形状。服务不接受时，检查当场报错，并说明不带它时可以正常回复。不接受的服务就用不了，我们不为它换发法（ADR-0019）。
- 格式说明从系统提示词的末尾挪到了共用固定部分。离用户这句话最近的，现在是这条靠后的系统消息。
- Gemini 这类缓存规律不明的服务，在这种排法和原来的排法下都命不中（实验里两种都是 0）。这只影响自带 LLM 的用户和换了服务的部署者。
- 改提示词结构会影响角色的表现。改动前后的回复对照稿见 `.scratch/prompt-caching/compare.md`。
